## 1. 원천 자료가 오는 형태

### 1-1. 원천 자료는 텍스트 파일입니다

원천 자료는 DB 덤프가 아니라 파이프(`|`)로 구분한 텍스트 파일입니다.

```
1111010100|서울특별시|종로구|청운동||0|144|3|111103100012|자하문로|0|94|0|...
```

- 헤더 행이 없고 첫 줄부터 데이터입니다
- 인코딩은 MS949입니다
- 줄 끝은 CRLF입니다. 마지막 칼럼을 읽을 때 `\r`를 떼지 않으면 빈 값이 채워진 값으로 잡힙니다
- 어느 칼럼이 무엇인지는 파일에 적혀 있지 않습니다. 칼럼의 순서와 이름과 자릿수는 `06-source-schema.md` 2절의 자료별 ERD에 옮겨 두었습니다
- 값이 없으면 빈 문자열로 옵니다

**실측 결과 파일마다 칼럼 개수가 한 종류로 일정했습니다.** 파이프가 값 안에 섞여 들어온 줄은 한 줄도 없었습니다.

### 1-2. 같은 내용을 2가지 방식으로 제공합니다

| | 건물DB (**채택**) | 주소DB |
|---|---|---|
| 방식 | 건물 한 채가 한 줄이고 주소 요소가 그 줄에 모두 있음 | 주소, 지번, 부가정보 3개 파일로 분리 |
| 장점 | 파일 하나로 주소가 완성됨 | 정규화되어 있음 |
| 단점 | 같은 값이 반복됨 | 조인해야 주소가 나옴 |

건물DB를 채택한 근거는 건물관리번호가 판정의 키(key)이고 건물DB가 그 번호를 중심으로 구성돼 있다는 점입니다.

### 1-3. 부속 자료

| 자료 | 담는 것 |
|---|---|
| 도로명코드 | 도로명 목록. 코드와 이름의 대응 |
| 도로명 | 도로명코드와 유일키가 같고 칼럼이 다릅니다. 부여사유가 여기에만 있습니다 |
| 관련지번 | 건물이 여러 지번에 걸칠 때의 **추가** 지번 |
| 상세주소DB | 다가구·원룸·단독주택과 상가·업무용 건물의 층·호 목록 |
| 상세주소 표시 (시군구용) | 상세주소DB와 사실상 같은 자료 |
| 상세주소 표시 (건축물대장) | 공동주택 호수 |
| 상세주소 동 표시 | 건물 이름 정보. 주소와 건물의 대응표 |
| 도로명주소 한글 | 같은 내용을 담은 또 다른 구성 방식 |

### 1-4. 전체분과 변동분

- 전체분은 현재 상태 전부를 담습니다
- 변동분은 지난달과 견주어 바뀐 것만 담고, 월 주기와 일 주기 2가지가 있습니다

**전체분에는 이력이 없습니다.** 자세한 내용은 4-8절에 있습니다.

## 3. 키: 파일을 무엇으로 잇는가

### 3-1. 법정동코드 (10자리)

`1111010100`은 법정동을 가리킵니다.

```
11      110      10100
시도     시군구     읍면동·리
```

행정동은 키로 쓸 수 없습니다. 자료건수 안내문의 원문은 다음과 같습니다.

> 현재 제공되는 행정동 정보는 관할주민센터 정보를 기준으로 하고 있으며 **도로명주소와 1:1로 매칭되는 정보만** 포함합니다. 또한 **행정동정보가 누락되거나 잘못 매칭된 정보가 존재할 수 있으므로** 참고용으로만 사용하시기 바랍니다.

- 1:N 대응은 아예 들어 있지 않습니다
- 원천 자료가 누락과 오매칭이 있다고 스스로 밝혔습니다
- 기준이 행정동 경계가 아니라 관할주민센터입니다

[전량] 건물DB의 행정동코드 칼럼에서 법정동과 행정동의 대응을 뽑을 수는 있습니다. 서울은 법정동 467개와 행정동 428개가 대응하고, 대응쌍은 883개입니다.

→ **대응표를 외부에서 얻지 않고 건물DB의 행정동코드 칼럼에서 뽑아 씁니다.** 행정동은 조회 키로 쓰지 않고 사유를 낼 때만 쓰므로 이 대응으로 충분합니다.

법정동코드는 행정구역이 개편되면 바뀝니다. 앞 5자리가 시군구코드이므로 시·도나 시·군·구가 재편되면 코드를 다시 매깁니다. [전량] 광주 북구 `2917010900`은 2026년 7월에 `1230010900`으로 바뀌었습니다. 그래서 법정동코드는 이름 대응을 잇는 키로 쓸 수 없습니다. 자세한 내용은 11-5절에 있습니다.

### 3-2. 건물관리번호 (25자리)

```
1111010100   1     0089    0003    031307
법정동코드(10) 산구분(1) 지번본번(4) 지번부번(4) 일련번호(6)
```

산구분은 1이 대지이고 2가 산입니다.

[전량] 건물관리번호 앞 10자리로 지역을 좁히면 안 됩니다.

| 대조 | 어긋난 비율 |
|---|---|
| 앞 10자리와 법정동코드 (전국) | 32.9% (3,524,146 / 10,722,871) |
| 본번·부번 부분과 현재 지번 (표본) | 9.0% (451 / 5,000) |

| 지역 | 10자리 불일치 | 5자리(시군구) 불일치 |
|---|---|---|
| 서울 | 0.30% | 0.00% |
| 경기 | 19.61% | 13.99% |
| 경북 | 3.81% | 0.00% |
| 제주 | 0.07% | — |

원인은 행정구역 개편입니다. 건물관리번호는 채번 시점의 코드를 그대로 담아 두고 바꾸지 않지만, 법정동코드 칼럼은 현재 코드를 담으므로 두 값이 달라집니다.

→ **지역은 법정동코드 칼럼으로 좁힙니다.** 건물관리번호의 중간 부분으로 지번을 유추해서도 안 됩니다.

→ 건물관리번호가 바뀌지 않는 이 성질이 옛 주소 대응을 만드는 재료입니다. 주소가 바뀌어도 건물관리번호는 바뀌지 않으므로, 갱신 전후에서 같은 번호를 견주면 옛 이름과 새 이름, 옛 등록주소와 새 등록주소를 함께 이을 수 있습니다. [전량] 2026년 7월 개편에서 광주 건물의 98.7%와 인천 건물의 96.7%가 번호를 그대로 유지했습니다. 자세한 내용은 8-6절에 있습니다.

### 3-3. 도로명 4칼럼 복합 키

```
도로명코드(12) + 지하여부(1) + 건물본번(5) + 건물부번(5)
```

사람이 쓰는 말로는 "자하문로 94"입니다. **이 키가 가리키는 것은 건물이 아니라 「등록주소 하나」입니다.**

건물DB 가이드 붙임4의 조인 조건 앞에는 `Select Distinct`가 붙어 있습니다. 가이드가 중복 행이 나온다는 것을 스스로 전제하고 있습니다.

### 3-4. 도로명코드 (12자리)

시군구코드(5)  도로명번호(7)

도로명코드는 도로명 이름이 바뀌어도 그대로 남습니다. 다만 행정구역이 개편되면 유지되지 않습니다. 앞 5자리가 시군구코드이므로 시·도나 시·군·구가 재편되면 코드를 전부 다시 매깁니다.

## 4. 자료마다 구조가 다릅니다

### 4-1. 지번이 자료 2곳으로 나뉩니다

```
대표지번  →  건물정보 파일 안의 칸 (지번본번 / 지번부번)
관련지번  →  별도 파일 (jibun_seoul.txt)
```

```
주소DB 지번_서울   612,836
  = 대표지번        523,345   (주소_서울 523,345와 정확히 일치)
  + 관련지번         89,491   (건물DB jibun_seoul 89,491과 정확히 일치)
```

### 4-6. 건물 유형은 법령이 정한 기준으로 판별합니다

건축법 시행령 별표1은 건물 유형을 다음 기준으로 나눕니다.

| 유형 | 기준 |
|---|---|
| 아파트 | 주택으로 쓰는 층수 5개 층 이상 |
| 연립주택 | 4개 층 이하 + 1개 동 바닥면적 합계 660㎡ 초과 |
| 다세대주택 | 4개 층 이하 + 660㎡ 이하 |
| 다가구주택 | 3개 층 이하 + 660㎡ 이하 + 각 실에 독립 주거 형태 없음 |

법 2개가 정한 「공동주택」의 범위가 서로 다릅니다.

| 법 | 공동주택에 드는 것 |
|---|---|
| 건축법 시행령 별표1 | 아파트 · 연립주택 · 다세대주택 · 기숙사 |
| 주택법 제2조제3호 | 아파트 · 연립주택 · 다세대주택 |

상세주소 부여 대상을 정하는 조문은 주택법을 가리킵니다.

행정안전부 주소기반산업지원서비스 안내는 동·층·호 표기를 다음과 같이 설명합니다.

- 동번호는 아라비아 숫자 일련번호나 한글로 적습니다 (`101동`·`102동` / `가동`·`나동`)
- 층수는 지상이면 일련번호로 적고 지하이면 `지하`를 붙입니다
- 호수는 `101호`·`102호` / `1호`·`2호` / `지하1호` / `지하101호`로 적습니다
- 표기할 때는 건물번호와 동·층·호 사이에 쉼표를 씁니다 (`삭주로 89, 201동 101호`)

도로명주소법 시행규칙 제25조④는 층·호를 생략하는 조건을 정합니다.

| 조건 | 생략 대상 |
|---|---|
| 건물번호로 동이 구분되는 경우 | 동번호 |
| 호수에 층수의 의미가 포함된 경우 | 층수 |
| 주거를 목적으로 하는 건물등에서 호수가 중복되지 않는 경우 | 층수 |
| 지하가 한 층인 경우 | 층수에 포함된 숫자 |

같은 시행규칙 제21조④는 층수를 생략하면 `동`·`호` 표기를 빼고 동번호와 호수를 하이픈으로 잇도록 정합니다.

도로명주소법 시행령 제11조의11은 상세주소를 부여하는 단위를 정합니다.

| 단위 | 뜻 |
|---|---|
| 동 | 지상으로 돌출된 형태로 구분되는 단위의 건물등 |
| 층 | 천장과 바닥면으로 구획된 공간 |
| 호 | 하나의 층에서 물리적인 경계로 구분되는 공간 |

하이픈을 정한 조문은 어디에도 없습니다. 시행규칙 제21조④가 하이픈을 언급하지만 층수를 생략했을 때의 표기 방법일 뿐입니다.

→ **그래서 하이픈으로 동·층·호를 판별하지 않습니다.**

### 4-7. 상세주소여부 칼럼의 뜻을 모릅니다

[전량] 상세주소여부가 `1`인 건물이 전국에 1,088,144채입니다. 그런데 상세주소DB에 실제로 줄이 있는 건물은 475,790채입니다. 반대로 상세주소여부가 `0`인데 줄이 있는 건물이 5,393채 있습니다.

**이 칼럼이 무슨 뜻인지 아직 모르므로 조회 분기에 쓰지 않습니다.**

[전량] 상세주소DB에 나오는 건물 481,183채 가운데 공동주택은 5,382채(1.1%)입니다.

## 7. 참조 캐시 구성

### 캐시는 후보를 좁히는 데만 씁니다

**실재 판정은 DB가 합니다.** `ExistenceVerifier`가 이 설계의 안전장치이므로 캐시가 낡아도 잘못된 확정으로 이어지지 않습니다.

| 캐시 오류 | 생기는 일 |
|---|---|
| 없어진 도로명을 담고 있습니다 | 후보로 나와도 `ExistenceVerifier`에서 걸러집니다 |
| 새 도로명을 모릅니다 | 후보 하나를 놓칩니다 |

새 도로명을 모르는 두 번째 줄에는 예외가 있습니다. 후보 자체를 만드는 부분은 새 값을 모르면 확인할 대상이 없습니다. 역조회 인덱스, 법정동 사전, 단위 표기 뗀 인덱스가 그렇습니다.

### 캐시는 층 6개로 이루어집니다

| 층 | 내용 | 규모 | 만드는 곳 |
|---|---|---|---|
| 상주 | 앞 세 자리 사전 | 1,677 | `ref.region`의 `stp` 1·2와 읍·면 |
| 상주 | 역조회 인덱스 (도로명 이름 → 시군구) | 167,217 | `ref.road` + `ref.address` |
| 상주 | 법정동 사전 (지번용) | 10,557 | `ref.region`의 `stp` 3·4 |
| 상주 | 단위 표기 뗀 인덱스 (키 → 층 + 원래 이름) | 142,576 | `ref.region` + `ref.road` |
| 상주 | 이름 대응 사전 (옛 이름 → 현재 이름) | 초기 0 | `ref.name_map` |
| 지연 | 시군구별 도로명 | 건당 최대 2,388 | 조회할 때 DB에서 읽어 적재합니다 |

단위 표기 뗀 인덱스는 단위 표기가 없는 토큰을 받습니다. 규칙과 실측은 `03-pipeline.md` 2절의 ①-2 단계에 있습니다.

이름 대응 사전이 읽는 `ref.name_map`은 서비스가 실행되는 동안 채워집니다. 처음에는 비어 있고 배치가 비교할 때마다 줄이 늘어납니다. 사전 자체는 항목 단위로 고치지 않고, 줄이 늘어난 날 통째로 다시 만들어 참조를 바꿉니다. 이 흐름은 `03-pipeline.md` 8절에 있습니다.

**없어진 등록주소는 `ref.addr_map`이 담고 상주 사전으로 적재하지 않습니다.** `ExistenceVerifier`가 후보를 모두 지운 뒤에만 조회하므로 상주 사전으로 둘 필요가 없습니다. 외부에서 받아 온 답은 `svc.legacy_map`이 담습니다.

### 상주 사전은 그 사전을 만든 배치가 끝날 때 교체합니다

**갱신 시점을 사전마다 따로 정하지 않습니다.** 사전이 읽는 테이블을 채우는 배치가 끝나면 그 사전을 교체합니다. 사전마다 주기를 두면 규칙이 사전 수만큼 늘어납니다.

사전은 통째로 새로 만들어 참조를 바꿉니다. 항목을 하나씩 고치면 반쯤 바뀐 사전으로 판정하는 순간이 생깁니다. 무상태 설계라 요청마다 사전을 새로 참조하므로, 실행 중인 요청은 옛 사전을 끝까지 씁니다.

일 변동분도 받습니다. 후보를 만드는 부분이라 새 값을 모르면 그 토큰이 사전에 잡히지 않고, 토큰을 하나도 찾지 못한 입력은 `AddressGate`에서 「주소가 아닙니다」로 응답합니다.

폐지된 값은 지우지 않습니다. `ExistenceVerifier`가 걸러 냅니다.

### 7-1. 사전을 수동으로 다시 만듭니다

자동 갱신만 두면 다음 배치까지 대응할 방법이 없는 경우가 4가지입니다.

| 언제 | 생기는 일 |
|---|---|
| 배치가 도중에 중단됐습니다 | `ref`는 새 값인데 사전은 옛 값입니다. 다음 날까지 어긋난 채로 응답합니다 |
| 대응 사전에 내부판정으로 한 줄을 넣었습니다 | 테이블에는 들어갔지만 메모리에는 올라가지 않습니다 |
| 교체만 실패했습니다 | 적재는 정상입니다. 배치 전체를 다시 실행할 이유가 없습니다 |
| 2단계에서 값을 바꿔 가며 측정합니다 | 사전을 다시 만들 때마다 배치 전체를 실행할 수 없습니다 |

**자동과 수동이 같은 코드를 호출합니다.**

```
사전 갈아 끼우기
 ├ 배치 끝에서 부른다      자동
 └ 운영 진입점에서 부른다   수동
```

자동과 수동을 따로 구현하면 규칙이 2개가 되고 한쪽만 고치는 일이 생깁니다. 이 결정은 「갱신 시점을 사전마다 따로 정하지 않습니다」와 어긋나지 않습니다. 그 결정은 자동 갱신 주기를 말하고, 수동 갱신은 주기가 아니라 사람이 호출하는 것입니다.

갱신 단위는 사전 하나입니다. 호출할 때 어느 사전인지 지정하고, 지정하지 않으면 전체 사전을 뜻합니다. 바뀌지 않은 사전까지 다시 만들면 시간과 힙을 두 배로 씁니다.

수동 갱신이 지켜야 할 것은 4가지입니다.

| 지킬 것 | 방법 |
|---|---|
| 통째로 만들어 참조를 바꿉니다 | 항목을 하나씩 고치지 않습니다. 자동 갱신과 같습니다 |
| 만들다 실패하면 옛 사전을 그대로 둡니다 | 반쯤 바뀐 사전으로 판정하는 순간을 만들지 않습니다 |
| 같은 사전을 동시에 두 번 만들지 않습니다 | 만드는 중에 다시 호출하면 「이미 실행 중입니다」를 반환합니다 |
| 교체 결과를 지표로 남깁니다 | 언제 · 어느 사전 · 몇 건 · 자동인지 수동인지 남깁니다 |

수동 갱신이 하지 않는 일은 다음과 같습니다.

```
사전 갱신     ref  →  메모리 사전        ref는 안 건드린다
적재 재실행   원천 파일  →  ref          다른 배치다
```

`ref`가 낡았으면 사전만 다시 만들어도 옛 값이 그대로 적재됩니다. 그때 필요한 것은 적재 배치를 다시 호출하는 일이고, 「같은 입력을 다시 넣어도 결과가 같아야 합니다」가 이미 그 상황을 다룹니다.

지연 적재 층은 갱신 대상이 아닙니다. 수동 갱신에는 「비웁니다」만 있으면 됩니다.

운영 진입점은 정제 API와 분리합니다. 인증과 호출 한도는 앞단이 맡는다는 결정이 여기에도 적용됩니다. 이 애플리케이션은 검증이 끝난 호출을 받아 사전을 다시 만들 뿐입니다. 운영 진입점 4개는 11-6절에 모아 두었습니다.

### 지연 적재 층에는 갱신 로직이 없습니다

지연 적재 층은 갱신하지 않고 버립니다. 다시 조회하면 DB에서 최신 값이 적재됩니다.

### 법정동 사전을 만드는 자료와 키

법정동 사전은 `ref.region`에서 만듭니다. `ref.token`에는 이름과 구분만 있어 코드를 줄 수 없습니다.

## 8. 갱신 서비스 흐름

**설계가 정하는 것과 구현이 정하는 것을 구분합니다.**

| 설계가 정합니다 | 구현이 정합니다 |
|---|---|
| 배치가 몇 개이고 언제 실행되는가 | SQL로 판단할지 애플리케이션 코드로 판단할지 |
| 각 배치가 무엇을 보고 분기하는가 | SQL 문장 형태 · 커밋 단위 · 배치 프레임워크 |
| 실패했을 때 다시 실행할 수 있는가 | 병렬 처리 여부 |
| 무엇을 지표로 남기는가 | |
| 순서에 매인 지점이 어디인가 | |

### 8-0. 배치 3개

```
[한 번]      월 전체분          →  ① 최초 적재  →  ref 전량 · 파생 생성
[매일]       일 변동분          →  ② 일 반영    →  폐지 판단 · 대응 비교 · 반영 · 파생 재구성
[매월]       월 전체분          →  ③ 월 대사    →  전체분을 정답으로 맞춘다 · 대응 비교
```

**대응 비교는 별도 배치가 아니라 ② 일 반영과 ③ 월 대사 안의 하위 컴포넌트 하나입니다.** 대응 비교는 덮어쓰기 직전에 갱신 전후를 비교하므로 그 지점에서만 실행할 수 있습니다.

배치에 파일을 넘기는 지점은 적재 진입점입니다. 적재 진입점이 받는 것과 남기는 것은 11-6절에 있고, 진입점 자체는 11-6절에 있습니다.

### 8-1. ① 최초 적재: 한 번만 실행합니다

*받는 것*: 월 전체분을 받습니다. 자료 10개 중 7개만 적재합니다.

| 적재하지 않는 자료 | 적재하지 않는 이유 |
|---|---|
| 관련지번 (건물DB) `jibun_` | 관련지번 한글 쪽과 같은 자료입니다. 전량 대조로 확인했습니다 |
| 도로명 `TN_SPRD_RDNM` | 고유 칼럼 4개(부여사유, 도로구간 기초번호 2개, 효력발생일)를 담지 않기로 했습니다. 나머지 칼럼은 도로명코드 자료에서 얻습니다 |
| 상세주소DB `adrdc_` | 시군구용과 사실상 같은 자료입니다. 시군구용에는 도로명주소관리번호 칼럼이 있고 여기에는 없습니다 |

*판단*: 판단할 것이 없습니다. 월 전체분에는 사유코드가 오지 않습니다(전량 확인).

*대응 비교*: 실행하지 않습니다. 비교할 이전 스냅샷이 없습니다. `ref.name_map`과 `ref.addr_map`은 비어 있는 채로 시작합니다.

*순서를 묶는 제약 3개*

| 제약 | 어디 | 내용 |
|---|---|---|
| 짝지어 읽습니다 | `ref.building` | 건물정보에 도로명주소관리번호 칼럼이 없습니다. 상세주소 동 표시 자료가 그 값을 제공합니다 |
| 두 자료가 행을 나눠 갖습니다 | `ref.lot` | 대표지번은 건물정보 안에 있고 나머지는 관련지번에 있습니다. 81.2% 대 18.8% |
| 파생 테이블은 맨 뒤에 만듭니다 | `ref.unit_lookup` · `ref.token` | 재료가 되는 마스터 테이블이 모두 적재된 뒤에 만듭니다 |

**`ref`에 외래키를 걸지 않으므로 마스터끼리는 순서가 자유롭습니다.** 위 제약 3개 말고는 순서에 매인 지점이 없습니다.

순서를 케이스로 적지 않고 제약으로 적습니다. 자료가 하나 늘면 순서 표를 다시 짜지 않고 그 자료가 위 제약 3개 중 어디에 걸리는지만 확인합니다.

*하위 컴포넌트를 2개로 나눕니다*

원천 복원이 먼저 실행되고 엔진 전환이 뒤에 실행됩니다. 파일을 읽어 원천 구조 그대로 `stg` 스테이징 테이블에 넣은 뒤, 그 값을 재해석해 `ref`를 만듭니다. 스테이징 테이블은 배치가 실행되는 동안에만 존재하고 영구 스키마로 남지 않습니다. 근거는 `decisions.md` 1-3-20절에 있습니다.

2개로 나눈 이유는 실패하는 지점이 다르기 때문입니다. 원천 복원은 파일이 깨졌을 때 실패하고, 엔진 전환은 재해석 규칙이 틀렸을 때 실패합니다. 하나의 하위 컴포넌트로 묶으면 어느 쪽에서 틀렸는지 구분할 수 없습니다.

아래 순서는 엔진 전환 하위 컴포넌트의 순서입니다. 원천 복원은 자료 7개를 어떤 순서로 넣어도 됩니다. 파일과 테이블이 하나씩 대응하고 서로를 참조하지 않기 때문입니다.

*순서*

```
마스터
  1  ref.region       도로명주소 한글       최하위 행만 온다. 상위 행은 뒷자리를 0으로 채워 만든다
  2  ref.road         도로명코드            읍면동 칸이 빈 줄. 전국분이라 지역 필터를 건다
  2  ref.road_emd     도로명코드            읍면동 칸이 찬 줄. 같은 파일을 조건으로 가른다
  3  ref.address      도로명주소 한글
  4  ref.address_lot  관련지번 (한글 쪽)
  5  ref.lot          건물정보 + 관련지번   양쪽에서 받아 넷(법정동코드·산여부·본번·부번)으로 중복을 없앤다
  6  ref.building     건물정보 + 동 표시    동 표시가 도로명주소관리번호를 채운다
  7  ref.unit         상세주소 표시 2세트   시군구용은 출처 S, 건축물대장은 출처 L

파생
  8  ref.unit_lookup  3 + 6 + 7
  9  ref.token        1 + 2 + 6
```

*순서 6번 `ref.building`에서 등록주소를 채우지 못하는 건물이 있습니다*: 서울 230채입니다. 잠실역 실내 도로명에 붙은 건물이 건물정보에는 있고 동 표시와 도로명주소 한글에는 없습니다. 이 건물은 등록주소를 비운 채로 넣습니다. 근거는 `02-data-model.md` 6-4절 `ref.building` 항목에 있습니다.

*상주 사전*: 배치가 끝난 뒤 사전 5개를 모두 만듭니다. 앞 세 자리 사전과 법정동 사전은 1번 `ref.region`을, 역조회 인덱스는 2번 `ref.road`와 3번 `ref.address`를, 단위 표기 뗀 인덱스는 1번 `ref.region`과 2번 `ref.road`를 재료로 씁니다. 이름 대응 사전은 재료가 아직 없으므로 빈 상태로 만듭니다.

*실패하면*: 처음부터 다시 실행합니다. 비우고 다시 넣는 것이 대사보다 비용이 적습니다.

*지표*: 자료별 적재 줄 수와 순서 6번 `ref.building`에서 등록주소를 채우지 못한 건물 수입니다. 서울에서 230채를 크게 벗어나면 동 표시 자료를 덜 읽은 것입니다. 줄 수는 적재 실행 로그의 파일 줄에 담습니다(11-6절).

### 8-2. ② 일 반영: 매일 실행합니다

*받는 것*: 일 변동분 파일을 받습니다.

*판단*: 줄마다 「폐지인가」 하나만 판단합니다.

```
폐지다      →  자료별 처리   건물·도로명·등록주소는 남기고 폐지 표시
                          관련지번·상세위치는 지운다
아니다      →  대응 비교 → 현재 값으로 만든다   신규와 변경을 구분하지 않는다
어느 쪽이든  →  건드린 등록주소를 모아 둔다
```

**폐지를 아는 방법이 자료마다 다릅니다.**

| 자료 | 무엇으로 아는가 |
|---|---|
| 도로명 · 도로명코드 | 사용여부 = 1로 압니다. 별도 칼럼이 있습니다 |
| 건물 · 등록주소 · 관련지번 · 상세위치 | 이동사유코드 = 63으로 압니다. 사용여부 칼럼이 없습니다 |

*대응 비교*: 덮어쓰기 직전에 실행합니다. 설계는 8-6절에 있습니다.

*마지막 하위 컴포넌트*: 모아 둔 등록주소만 파생 테이블에서 지우고 다시 만듭니다. [전량] 7월 기준 15,361곳이고, 서울 상세주소 4,323,373줄 중 38,541줄(0.89%)을 다시 씁니다.

*실패하면*: 처리한 등록주소를 기록하며 등록주소 단위로 커밋합니다. 중단된 지점부터 이어서 실행합니다.

*지표*: 사유코드별 건수, 삭제·삽입 건수, 새로 만든 대응 줄 수입니다. 평소 범위를 벗어나면 배치를 멈춥니다.

*역조회 인덱스*: 신규만 넣습니다. 폐지와 변경은 반영하지 않습니다. 반영하지 않은 값이 후보로 나와도 `ExistenceVerifier`가 걸러 냅니다.

*앞 세 자리 사전 · 법정동 사전 · 단위 표기 뗀 인덱스*: `ref.region` 또는 `ref.road`가 바뀐 날만 다시 만듭니다. 사전 전체를 새로 만든 뒤 참조를 바꿉니다.

*이름 대응 사전*: `ref.name_map`에 줄이 늘어난 날만 다시 만듭니다.

### 8-3. ③ 월 대사: 매월 실행합니다

*하는 일*: 월 전체분을 정답으로 보고 현재 값과 맞춥니다.

```
전체분에만 있음   → 넣는다
현재 값에만 있음  → 자료별 처리. ② 일 반영의 폐지 갈래와 같다
값이 다름         → 대응 비교 → 전체분 값으로 맞춘다
```

*판단*: 판단을 두지 않습니다. 분기 3가지 모두 월 전체분을 따릅니다. 근거는 팀프레시 장애 대응 경험입니다. 일 변동분에 없고 월 전체분에 있는 주소는 전체분 쪽이 맞았습니다.

*두 번째 분기의 처리는 ② 일 반영과 같습니다.* 전체분은 살아 있는 것만 담으므로 「현재 값에만 있다」와 「폐지됐다」가 같은 사실입니다. 그래서 처리도 같아야 합니다. 건물과 도로명과 등록주소는 남기고 폐지 표시하며 관련지번과 상세위치는 지웁니다. 자료별 갈래는 8-2절에 있습니다.

이 분기를 자료를 가리지 않고 삭제로 두면 ② 일 반영이 붙인 폐지 표시가 다음 달 월 대사에서 지워집니다. 두 배치가 같은 사실을 놓고 다르게 행동하면 폐지 표시가 한 달을 넘기지 못합니다.

*왜 있는가*: **일 변동분을 하루라도 놓치면 그 뒤로 계속 어긋난 상태가 이어집니다.** 월 대사가 그 상태를 되돌립니다. 일 반영이 완벽하다는 전제를 세우지 않기 위한 장치입니다.

*지표*: 어긋난 건수 자체가 지표입니다. 건수가 0에서 멀어지면 ② 일 반영에 빠뜨린 부분이 있다는 뜻입니다.

*상주 사전*: 사전 5개를 모두 새로 만들어 전체를 교체합니다.

### 8-4. 배치 3개에 공통으로 걸리는 요구: 다시 실행해도 같은 결과

**같은 입력을 다시 넣어도 결과가 같아야 합니다.**

배치는 중간에 멈출 수 있고 같은 파일이 두 번 들어오기도 합니다. 다시 실행했을 때 값이 달라지면 어디까지 처리했는지를 사람이 추적해야 하고, 그때부터 운영이 사람 손에 의존하게 됩니다.

이 요구에서 「신규와 변경을 구분하지 않습니다」라는 처리 방식이 나왔습니다. 신규를 삽입으로만 처리하면 두 번째 실행에서 키 충돌로 멈춥니다. 「현재 값으로 만듭니다」로 두면 몇 번을 실행해도 결과가 같습니다.

대응 비교도 같은 성질을 지킵니다. 같은 두 스냅샷을 다시 비교하면 같은 대응이 나오고, 이미 있는 줄은 덮어씁니다.

상주 사전도 같습니다. 사전 전체를 다시 만들므로 몇 번을 실행해도 같은 사전이 나옵니다.

적재 진입점도 같습니다. 같은 폴더를 두 번 넣어도 결과가 같아야 합니다. 적재 진입점은 11-6절에 있습니다.

구현이 SQL이든 애플리케이션 코드든 이 성질을 만족해야 합니다.

### 8-5. 사유코드를 테이블로 쌓지 않습니다

② 일 반영이 사유코드를 읽지만 읽은 값을 테이블로 쌓지 않습니다. 사유코드는 분기를 나누는 데만 쓰고 버립니다.

**원천 이력은 무엇이 무엇으로 바뀌었는지를 알려 주지 않습니다.** 도로명 폐지 71줄의 변경이력정보가 전부 비어 있고, 변경이력사유 `0`(도로명변경)이 전체분에도 변동분에도 없습니다(10-3절).

그래서 원천 이력을 옮겨 담는 테이블은 만들지 않습니다. 대신 우리가 갱신 전후를 비교해 대응을 만듭니다. 아래 8-6절이 그 처리를 다룹니다.

남기는 것은 지표입니다. 사유코드별 건수, 삭제·삽입 건수, 새로 만든 대응 줄 수를 배치 실행 기록으로 남깁니다.

### 8-6. 대응 비교: 갱신 전후를 비교합니다

설계 전체는 `03-pipeline.md` 8절에 있습니다. 여기서는 대응 비교가 배치 안에서 차지하는 부분만 적습니다.

*재료*: 건물관리번호 하나입니다. 건물관리번호는 주소가 바뀌어도 그대로이고 행정구역이 개편되어도 유지됩니다. 도로명코드와 법정동코드는 개편에서 함께 재채번되므로 키로 쓰지 않습니다(3-4절).

*실행 지점*: **덮어쓰기 직전입니다.** ② 일 반영과 ③ 월 대사 안에서 「현재 값으로 만듭니다」 바로 앞에 놓입니다. 덮어쓴 뒤에는 비교할 옛 값이 없습니다.

*비교하는 것*: 같은 건물관리번호의 주소 전후입니다. 한 번 비교하면 이름 대응과 주소 대응이 함께 나옵니다.

| 달라진 곳 | 어디로 |
|---|---|
| 시도 · 시군구 · 읍면동 이름 | `ref.name_map` |
| 도로명 이름 | `ref.name_map` |
| 도로명주소관리번호 | `ref.addr_map` |

*입력을 스냅샷 2개로 정의합니다*

```
비교 배치
  입력   이전 스냅샷 · 새 스냅샷
  일     같은 건물관리번호끼리 이름과 자리를 견준다
  출력   달라진 것마다 대응 한 줄
```

| 호출하는 지점 | 이전 스냅샷 | 새 스냅샷 | 출처 칼럼 |
|---|---|---|---|
| ② 일 반영 · ③ 월 대사 | 현재 `ref` | 스테이징에 올린 새 자료 | 배치비교 |
| 과거분을 넣을 때 | 스테이징에 올린 과거 전체분 | 현재 `ref` | 과거연동 |

스냅샷 2세트가 어디서 왔는지 배치가 묻지 않습니다. 그래서 2024년 8월 전체분을 스테이징에 올리고 대응 비교를 한 번 더 호출하면 전남광주통합특별시와 인천 개편 대응이 한꺼번에 만들어집니다. 새 코드를 작성하지 않아도 됩니다.

*옛 이름 하나가 현재 이름 여러 개로 나뉠 수 있습니다*: 인천 서구가 서해구와 검단구로 나뉩니다. 이때는 대응 줄을 여러 개 만들고 조회에서 `EXACT`와 `MANY`로 구분해 반환합니다.

*과거연동의 한계*: 두 시점만 비교하므로 그 사이에 두 번 바뀐 주소는 한 번 바뀐 것으로 보입니다. 출처 칼럼이 그 사실을 남깁니다.

*실패하면*: 대응 줄은 덮어쓰기이므로 다시 실행해도 결과가 같습니다. 중단된 지점부터 이어서 실행합니다.

*지표*: 새로 만든 대응 줄 수입니다. 평소 범위를 크게 벗어나면 이전 스냅샷을 잘못 지정한 것입니다.

## 9. 지번 표기 규칙

**원천 자료에는 주소를 표기한 문자열이 없습니다.** 어느 파일도 「서울특별시 종로구 자하문로 94」라는 문자열을 그대로 제공하지 않습니다.

그래서 표기 규칙을 자료에서 역산할 수 없습니다. 사람이 입력한 문자열을 어떤 칼럼으로 나눌지는 법령에서 가져옵니다.

### 근거 조문

표기 규칙의 근거는 「공간정보의 구축 및 관리 등에 관한 법률」과 그 시행령입니다.

| 대상 | 조문 | 내용 |
|---|---|---|
| 지번의 정의 | 법 제2조 22호 | 필지에 부여해 지적공부에 등록한 번호입니다 |
| 동·리가 앞에 오는 근거 | 법 제2조 23호 | 지번부여지역은 동·리 또는 이에 준하는 지역입니다 |
| 임야 표시 | 시행령 제56조① | 임야대장·임야도에 등록하는 토지는 숫자 앞에 `산`을 붙입니다 |
| 본번과 부번 | 시행령 제56조② | 둘 사이를 `-`로 잇습니다. 이 표시는 「의」라고 읽습니다 |

「의」라고 읽는다는 규정은 실무에 영향을 줍니다. 사용자가 「150의 3」으로 입력한 문자열도 조문에 근거가 있는 표기입니다.

### 「이에 준하는 지역」은 `가`로 끝나는 이름입니다

[전량 · 전국] 법정읍면동은 3,589개이고 법정리는 6,968개입니다.

| 끝 글자 | 개수 |
|---|---|
| `동` | 2,079 |
| `면` | 1,006 |
| `가` | 266 |
| `읍` | 236 |
| `로` | 2 |

법정리는 전량 `리`로 끝납니다. 한자를 괄호로 병기한 리가 6개 있습니다.

`가`로 끝나는 이름이 「이에 준하는 지역」에 해당합니다.

[전량 · 전국] 도로명과 법정동·리 이름이 겹치는 이름은 2개이고, `남성로`와 `세종로`입니다.

## 10. 변경 이력: 무엇이 채워지고 무엇이 채워지지 않는가

### 10-1. 말소일자는 원천에 오지 않습니다

| 자료 | 사용여부 | 말소일자 |
|---|---|---|
| 도로명코드 전체분 (371,958줄) | 전량 `0` | 전량 빈 값 |
| 도로명 전체분 (371,921줄) | 전량 `0` | 전량 빈 값 |
| 도로명코드 변동분 (434줄) | `0` 363 / `1` 71 | 전량 빈 값 |
| 도로명 변동분 (541줄) | `0` 470 / `1` 71 | 전량 빈 값 |

**말소일자는 쓸 수 없는 칼럼입니다.**

줄 끝의 `\r`를 제거하지 않으면 마지막 칼럼이 채워진 값으로 잘못 집계됩니다.

### 10-2. 없어진 도로명은 변동분에만 나타납니다

전체분은 살아 있는 도로명의 스냅샷이므로 사용여부가 전부 `0`입니다. 변동분에는 그달에 없어진 도로명이 사용여부 `1`로 71건 들어 있습니다. 이 71건은 그달에 한 번만 나타나고 다음 달 변동분에는 없습니다.

**전체분 2세트를 비교해도 같은 결과가 나옵니다.** 6월과 7월을 비교하면 6월에만 있는 키 71개와 7월에만 있는 키 363개가 나왔습니다. 자세한 내용은 4-8절에 있습니다.

### 10-3. 폐지 건에는 대응 관계가 없습니다

| 자료 | 변경이력사유 | 변경이력정보 |
|---|---|---|
| 도로명코드 변동분 | 빈값 363 / `1` 폐지 71 | 「신규」 363 / 빈값 71 |
| 도로명 변동분 | 빈값 363 / `9` 기타 107 / `1` 폐지 71 | 「신규」 363 / 빈값 178 |

**없어진 71건은 변경이력정보가 전부 비어 있습니다.**

변경이력사유 `0`(도로명변경)은 전체분에도 변동분에도 한 건도 없습니다.

이것이 원천 이력을 옮겨 담지 않는 근거입니다. 다만 대응 관계를 만드는 일 자체를 포기하는 근거는 아닙니다. 건물관리번호가 개편을 건너므로 갱신 전후를 비교하면 대응 관계가 나옵니다. 자세한 내용은 8-6절에 있습니다.

### 10-4. 이전도로명주소도 채워지지 않습니다

이전도로명주소는 도로명주소 한글 자료의 18번째 칼럼입니다. **전체분 16개 시도와 변동분 9,785줄이 전부 빈 값입니다.**

## 11. 원천 자료를 받는 방법과 남길 파일

연계 API는 기관 신청만 받고, 개인은 주소기반산업지원서비스 화면에서 내려받습니다(홈 > 주소정보 자료제공 > 주소정보 다운로드). **그래서 이 설계는 파일을 입력으로 삼습니다.** 배치의 입력이 이미 「스테이징에 올린 2세트」로 정의되어 있으므로(`03-pipeline.md` 8-5절) 자료를 받는 방법이 바뀌어도 배치는 바뀌지 않습니다.

### 11-1. 자료 묶음 6개 가운데 4개를 받습니다

| 묶음 | 받는지 | 근거 |
|---|---|---|
| 건물DB | 받습니다 | 건물정보와 도로명코드가 이 묶음에 있습니다 |
| 도로명주소 한글 | 받습니다 | 등록주소와 관련지번이 이 묶음에 있습니다 |
| 상세주소 표시 | 받습니다 | 시군구용과 건축물대장용 2세트가 이 묶음에 있습니다 |
| 상세주소 동 표시 | 받습니다 | 건물의 도로명주소관리번호를 제공합니다 |
| 주소DB | 받지 않습니다 | 건물DB를 골랐습니다. 이 묶음에 든 `개선_도로명코드_전체분.txt`는 칼럼이 17개라 우리가 쓰는 칼럼 20개짜리 `road_code`와 다른 파일입니다 |
| 상세주소DB | 받지 않습니다 | 시군구용과 같은 자료이고 도로명주소관리번호 칼럼이 없습니다 |

### 11-2. 압축을 푼 뒤 남기는 파일

| 자료 폴더 | 전체분 | 변동분 | 적재 대상 |
|---|---|---|---|
| `building-db` | `build_{시도}.txt` | `build_mod.txt` | 건물정보 |
| `building-db` | `road_code_total.txt` | `road_code_mod.txt` | 도로명코드 |
| `road-address-kor` | `rnaddrkor_{시도}.txt` | `rnaddrkor_mod.txt` | 도로명주소 한글 |
| `road-address-kor` | `jibun_rnaddrkor_{시도}.txt` | `jibun_rnaddrkor_mod.txt` | 관련지번 |
| `detail-address-display` | `rnspbd_adrdc_{시도}.txt` | `rnspbd_adrdc_mod.txt` | 상세주소 표시 시군구용 |
| `detail-address-display` | `rnspbt_adrdc_{시도}.txt` | `rnspbt_adrdc_mod.txt` | 상세주소 표시 건축물대장 |
| `detail-address-dong` | `rnspbd_dong_{시도}.txt` | `rnspbd_dong_mod.txt` | 상세주소 동 표시 |

**버리는 파일은 `jibun_{시도}.txt` 하나뿐입니다.** 이 파일은 건물DB 안에 있고, 도로명주소 한글 묶음의 `jibun_rnaddrkor_*`와 같은 자료입니다. 두 이름이 비슷해서 묶음 단위로 지우는 방식으로는 걸러지지 않습니다.

`[가이드]*.pdf`와 `[자료건수]*.txt`는 자료 폴더에 두지 않고 `{연-월}_source/guide/`로 옮깁니다. 적재 진입점은 자료 폴더만 훑으므로 이 두 종류가 「모르는 파일」로 잡히지 않고, 그래야 원천이 파일을 새로 얹은 날 그 이름이 지표에서 바로 드러납니다.

적재 진입점이 알아야 할 원천 파일의 성질이 2가지입니다. `road_code_total.txt`는 전국 파일 한 세트여서 시도별로 나뉘지 않습니다. 변동분은 자료마다 `_mod.txt` 파일이 하나이고, 이 파일도 전국 파일 한 세트입니다.

### 11-3. 폴더 규약: 한 계층이 사실 하나만 담습니다

```
{연-월}_source / {구분} / {자료} / {원천 파일명}
2026-07_source / full   / building-db / build_seoul.txt
```

| 계층 | 값 | 정하는 것 |
|---|---|---|
| 연-월 | `2024-08` · `2026-06` · `2026-07` | 어느 달에 배포한 자료인가 |
| 구분 | `full` · `changes` | 전체분인가 변동분인가 |
| 자료 | 위의 폴더 4개 | 어느 묶음인가 |
| 파일명 | 원천 그대로 | 어느 자료이고 어느 시도인가 |

**원천이 준 폴더 이름을 그대로 쓰지 않습니다.** 원천 이름을 그대로 쓰면 하위 폴더 이름에 연월과 구분이 되풀이되어 같은 값을 두 번 읽게 됩니다.

파일명은 원천 그대로 둡니다. 파일명이 자료와 시도를 이미 담고 있고, 파일명을 고치면 가이드 문서와 대조할 수 없게 됩니다.

### 11-4. 내려받는 자료의 범위

| 세트 | 받는 이유 |
|---|---|
| 2024-08 전체분 | 과거연동에 씁니다. 개편 전 이름을 담은 유일한 세트이고, 건물DB 묶음만 있으면 됩니다 |
| 2026-06 전체분 | 개편이 시행 전에 반영된다는 것을 확인한 세트입니다 |
| 2026-07 전체분 | 최초 적재의 정답이 되는 세트입니다 |
| 2026-07 변동분 | 일 반영 배치를 시험할 재료입니다 |

**2026-06 변동분은 받지 않습니다.** 전체분 2세트를 비교하면 그 사이에 바뀐 것이 모두 나옵니다.

### 11-5. 한 달 전 세트로는 안 되는 이유

[전량] 2026년 6월 30일 기준 자료에 이미 전남광주통합특별시가 있습니다. 시도가 16개로 7월과 같고, 6월 세트와 7월 세트 사이에 이름이 바뀐 것이 시도·시군구·읍면동·도로명 모두 0건입니다.

2세트의 기준 시점이 서로 다른 것은 맞습니다. 고시일자 최대값이 6월분은 `20260630`, 7월분은 `20260731`입니다. 줄 수도 371,666과 371,958로 다릅니다.

→ **행정안전부가 시행 전에 개편 내용을 미리 담습니다.** 며칠 앞서 담는지는 측정하지 않았습니다.

### 11-6. 적재 진입점

이 절은 파일에서 스테이징까지를 맡는 하위 컴포넌트 한 개를 다룹니다. 그 뒤의 처리는 8절의 배치 3개가 이어받습니다.

#### 적재 진입점이 받는 입력 2개

| 입력 | 값 |
|---|---|
| 폴더 | `{연-월}_source/{구분}` 계층까지 |
| 배치 종류 | 최초적재 · 일반영 · 월대사 · 과거연동 |

**폴더만으로는 모자랍니다.** 최초 적재와 월 대사와 과거연동이 모두 `full` 폴더를 받고, 과거연동은 대응 비교의 스냅샷 방향까지 뒤집습니다(8-6절). 경로가 담는 사실은 연월과 구분뿐이고, 어느 배치인지는 경로에 없습니다.

배치 종류는 목록이 아니라 값 하나로 받습니다. 그래서 「사람이 목록을 적지 않습니다」라는 원칙과 어긋나지 않습니다.

구분 계층까지 받는 이유는 한 번의 실행이 전체분이거나 변동분이지 둘 다가 아니기 때문입니다. 이 두 계층을 받으면 연월과 구분은 경로에서 읽고, 자료와 시도는 그 아래에서 읽습니다.

구분과 배치 종류가 어긋나면 멈춥니다. `changes` 폴더를 주면서 최초 적재를 호출하는 것이 그런 경우입니다.

#### 파일을 고르는 규칙: 자료 폴더와 접두어를 짝으로 맞춥니다

접두어만 보면 두 지점에서 걸립니다. `jibun_`은 버리고 `jibun_rnaddrkor_`는 적재하며, `rnspbd_adrdc_`와 `rnspbd_dong_`은 앞 7글자가 같습니다.

**자료 폴더와 접두어를 짝으로 맞추면 특례가 필요 없습니다.** 버리는 `jibun_`은 `building-db`에 있고 적재하는 `jibun_rnaddrkor_`는 `road-address-kor`에 있으므로, 자료 폴더마다 접두어 목록을 따로 두면 어느 쪽도 다른 폴더의 목록에 걸리지 않습니다.

| 자료 폴더 | 접두어 |
|---|---|
| `building-db` | `build_` · `road_code_` |
| `road-address-kor` | `rnaddrkor_` · `jibun_rnaddrkor_` |
| `detail-address-display` | `rnspbd_adrdc_` · `rnspbt_adrdc_` |
| `detail-address-dong` | `rnspbd_dong_` |

접두어를 떼고 남는 값이 시도입니다. 예외는 11-2절에 적어 둔 원천 파일의 성질 2가지입니다. 구분이 `changes`면 남는 값이 `mod` 하나이고 전국 파일 한 세트이며, 구분이 `full`이고 남는 값이 `total`이면 도로명코드의 전국 파일 한 세트입니다.

검사는 있어야 할 파일이 있는지를 보는 방식으로 합니다. 접두어 7개마다 파일이 한 개 이상 있는지만 봅니다. 시도 수는 고정하지 않습니다. 서울만 받은 폴더도 정상이고, 과거연동은 건물DB 묶음만 있으면 됩니다.

모르는 파일은 건너뛰고 그 이름을 지표에 남기며 멈추지 않습니다. 원천이 파일을 하나 더 추가했다고 그날 운영이 깨지면 안 되고, 「자료마다 담는 범위가 다른 것이 정상입니다」라는 원칙이 여기에도 적용됩니다. 멈추는 것은 반대쪽 경우입니다. 적재 대상인데 파일이 없으면 멈춥니다.

#### 적재 실행 로그: 테이블 2개

**한 테이블에 담으면 배치 종류와 연월과 구분이 파일 줄마다 되풀이되어 제3정규형을 위반합니다.** 실행이 끝난 시각을 적을 때 서울은 7줄을, 전국이면 97줄을 함께 고쳐야 하고, 하나를 놓치면 같은 실행이 서로 다른 두 시각을 담게 됩니다. 폴더가 비면 파일 줄이 없어서 배치를 호출했으나 아무것도 고르지 못했다는 사실이 아예 남지 않습니다.

| 테이블 | 한 줄이 담는 것 | 논리명 |
|---|---|---|
| `svc.load_run` | 실행 하나 | 적재실행 |
| `svc.load_file` | 파일 하나 | 적재파일 |

칼럼은 `02-data-model.md` 6-4절에 있습니다.

파일 줄의 키는 적재실행식별자와 원천파일명입니다. 건너뛴 파일은 자료와 시도를 채우지 못하므로 그 2개를 키로 쓸 수 없습니다. 파일명은 폴더 안에서 유일하고 원천 그대로 두기로 이미 정해 둔 값입니다.

두 테이블을 두는 스키마는 `svc`입니다. 스키마를 나눈 근거가 「온라인이 참조 마스터를 고치는 길을 권한으로 막습니다」인데, 적재 실행 로그는 배치만 쓰고 온라인은 읽지 않습니다. `ref`는 원천에서 나온 참조 자료를 담는 스키마라 성격이 다르고, 테이블 2개 때문에 스키마를 4개로 늘리는 것은 타당하지 않습니다.

적재 실행 로그는 판단에 관여하지 않습니다. 적재는 「현재 값으로 만듭니다」를 따르므로 같은 폴더를 두 번 넣어도 결과가 같습니다(8-4절). 적재 실행 로그를 보고 이미 넣은 파일을 건너뛰게 만들면 로그가 틀렸을 때 적재도 함께 틀립니다. 실패한 지점부터 이어서 실행하는 일은 8-2절의 지점 단위 커밋이 맡습니다.

#### 운영 진입점 4개

| 진입점 | 하는 일 |
|---|---|
| 적재 | 폴더와 배치 종류를 받아 배치를 실행합니다 |
| 사전 갈아 끼우기 | 상주 사전을 통째로 다시 만듭니다. 자동 실행과 같은 코드를 씁니다 (7-1절) |
| 지연 적재 층 비우기 | 고치지 않고 버립니다 (7-1절) |
| 진행 상태 보기 | 적재 실행 로그를 읽어 실행 중인지, 마지막 실행이 언제인지 알려 줍니다 |

**진입점 4개가 규칙 3개를 함께 지킵니다.**

- 정제 API와 분리해 둡니다. 인증과 호출 한도는 앞단이 맡습니다
- 실행 중에 다시 호출하면 이미 실행 중이라는 응답을 돌려줍니다. 적재 실행 로그의 실행결과 칼럼이 그 값을 담습니다
- 호출한 결과를 지표로 남깁니다
