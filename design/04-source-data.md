## 1. 자료가 어떤 모양으로 오는가

### 1-1. 텍스트 파일이다

DB 덤프가 아니라 파이프(`|`) 구분 텍스트 파일이다.

```
1111010100|서울특별시|종로구|청운동||0|144|3|111103100012|자하문로|0|94|0|...
```

- 헤더 행 없음. 첫 줄부터 데이터
- 인코딩 **MS949**
- 줄 끝이 **CRLF**다. 마지막 칸을 볼 때 `\r`를 떼지 않으면 빈 값이 채워진 값으로 잡힌다
- 어느 칸이 무엇인지 파일에 안 적혀 있다. **가이드 PDF를 봐야 안다**
- 값이 없으면 빈 문자열

**실측: 파일마다 컬럼 개수가 한 종류로 일정했다.** 파이프가 값 안에 섞여 들어온 줄이 한 줄도 없다.

### 1-2. 같은 내용이 두 방식으로 포장돼 있다

| | 건물DB (**채택**) | 주소DB |
|---|---|---|
| 방식 | 건물 한 채가 한 줄. 주소 요소가 그 줄에 다 있음 | 주소 / 지번 / 부가정보 세 파일로 분리 |
| 장점 | 파일 하나로 주소 완성 | 정규화되어 있음 |
| 단점 | 같은 값이 반복됨 | 조인해야 주소가 나옴 |

채택 근거의 핵심은 **건물관리번호가 판정의 열쇠**이고 건물DB가 그것을 중심으로 짜여 있다는 것.

### 1-3. 부속 자료

| 자료 | 담는 것 |
|---|---|
| 도로명코드 | 도로명 목록. 코드 ↔ 이름 대응 |
| 도로명 | 도로명코드와 유일키가 같고 칸이 다르다. 부여사유가 여기에만 있다 |
| 관련지번 | 건물이 여러 지번에 걸칠 때의 **추가** 지번 |
| 상세주소DB | 다가구·원룸·단독주택과 상가·업무용 건물의 층·호 목록 |
| 상세주소 표시 (시군구용) | 상세주소DB와 사실상 같은 자료 |
| 상세주소 표시 (건축물대장) | **공동주택 호수** |
| 상세주소 동 표시 | 건물 이름 정보. 주소 ↔ 건물 매핑표 |
| 도로명주소 한글 | 또 다른 포장 방식 |

### 1-4. 전체분과 변동분

- **전체분** — 현재 상태 전부
- **변동분** — 지난달 대비 바뀐 것만 (월·일 두 주기)

**중요: 전체분에는 이력이 없다.** → 4-8 참조

## 3. 키 — 파일을 무엇으로 잇는가

### 3-1. 법정동코드 (10자리)

`1111010100` — 동네를 가리킨다.

```
11      110      10100
시도     시군구     읍면동·리
```

**행정동은 키로 쓸 수 없다.** 자료건수 안내문의 원문:

> 현재 제공되는 행정동 정보는 관할주민센터 정보를 기준으로 하고 있으며 **도로명주소와 1:1로 매칭되는 정보만** 포함합니다. 또한 **행정동정보가 누락되거나 잘못 매칭된 정보가 존재할 수 있으므로** 참고용으로만 사용하시기 바랍니다.

- 1:N인 경우는 아예 안 들어 있다
- 누락과 오매칭을 원천이 인정했다
- 기준이 행정동 경계가 아니라 **관할주민센터**다

**[전량] 건물DB 행정동코드 칸에서 대응을 뽑을 수는 있다.** 서울 법정동 467 ↔ 행정동 428, 대응쌍 883이다.

→ **[확인 필요: 행정동 ↔ 법정동 대응표를 어디서 얻는가]**

**법정동코드는 행정구역 개편에서 바뀐다.** 앞 5자리가 시군구코드이므로 시·도나 시·군·구가 재편되면 코드가 다시 매겨진다. **[전량] 광주 북구 `2917010900`이 2026년 7월에 `1230010900`이 됐다.** 그래서 이름 대응을 잇는 열쇠로 쓸 수 없다. 14-5절에 있다.

### 3-2. 건물관리번호 (25자리)

```
1111010100   1     0089    0003    031307
법정동코드(10) 산구분(1) 지번본번(4) 지번부번(4) 일련번호(6)
```

산구분: **1 = 대지, 2 = 산**

**[전량] 앞 10자리로 지역을 좁히면 안 된다.**

| 대조 | 어긋난 비율 |
|---|---|
| 앞 10자리 vs 법정동코드 (전국) | **32.9%** (3,524,146 / 10,722,871) |
| 본번·부번 자리 vs 현재 지번 (표본) | 9.0% (451 / 5,000) |

| 지역 | 10자리 불일치 | 5자리(시군구) 불일치 |
|---|---|---|
| 서울 | 0.30% | 0.00% |
| 경기 | 19.61% | 13.99% |
| 경북 | 3.81% | 0.00% |
| 제주 | 0.07% | — |

**원인은 행정구역 개편이다.** 건물관리번호는 채번 시점의 코드를 굳혀 넣고 바꾸지 않는데, 법정동코드 칸은 현재값이라 갈린다.

→ **지역은 법정동코드 칸으로 좁힌다.** 중간 자리로 **지번 유추**도 하면 안 된다.

→ **바로 이 성질이 옛 주소 대응을 만드는 재료다.** 주소가 바뀌어도 건물관리번호는 안 바뀌므로, 갱신 전후에서 같은 번호를 견주면 옛 이름과 새 이름, 옛 자리와 새 자리가 함께 이어진다. **[전량] 2026년 7월 개편에서 광주 건물 98.7%, 인천 건물 96.7%가 번호를 그대로 지켰다.** 8-6절에 있다.

### 3-3. 도로명 4칸 묶음

```
도로명코드(12) + 지하여부(1) + 건물본번(5) + 건물부번(5)
```

사람 말로는 **"자하문로 94"**. **이 키가 가리키는 것은 건물이 아니라 「주소 한 자리」다.**

건물DB 가이드 붙임4의 조인 조건 앞에 `Select Distinct`가 붙어 있다. **가이드 스스로 중복 행을 전제한다.**

### 3-4. 도로명코드 (12자리)

```
11110      3100012
시군구코드(5)  도로명번호(7)
```

**유일키는 도로명코드(12) + 읍면동일련번호(2) = 14자리다.**

**도로명코드는 도로명 이름이 바뀌어도 안 바뀐다. 다만 행정구역 개편은 못 건넌다.** 앞 5자리가 시군구코드이므로 시·도나 시·군·구가 재편되면 코드가 통째로 다시 매겨진다.

**[전량] 2024년 8월과 2026년 7월 대조**

| 잰 것 | 값 |
|---|---|
| 2024-08 광주(29)·전남(46) 도로명코드 열쇠 38,020개 중 2026-07 생존 | **0** |
| 2026-07 통합(12) 열쇠 38,284개 중 2024-08에 있던 것 | **0** |
| 코드가 유지된 채 이름만 바뀐 도로명 (21개월 전국) | **1건** (경기 어수마을6길 → 어수마을1길) |

→ **이름 대응을 잇는 열쇠는 도로명코드가 아니라 건물관리번호다.** `03-pipeline.md` 8-1절에 있다.

## 4. 자료마다 생김새가 다른 것

### 4-1. 지번이 두 군데로 나뉜다

```
대표지번  →  건물정보 파일 안의 칸 (지번본번 / 지번부번)
관련지번  →  별도 파일 (jibun_seoul.txt)
```

```
주소DB 지번_서울   612,836
  = 대표지번        523,345   (주소_서울 523,345와 정확히 일치)
  + 관련지번         89,491   (건물DB jibun_seoul 89,491과 정확히 일치)
```

→ **도로명주소 한 자리에 대표지번이 정확히 하나씩 있다.**

**지번일련번호는 순번이 아니다.** 전역 시퀀스로 보이고 **대표 여부를 뜻하지 않는다.**

### 4-2. 건물 이름이 세 칸으로 흩어진다

| 칸 | 값 | [표본] 빈값률 |
|---|---|---|
| 건축물대장건물명 | `강일리버파크` | 86.9% |
| 상세건물명 | `308동` | 89.5% |
| 시군구용건물명 | `강일리버파크3단지아파트` | 74.1% |

> **공동주택이 아닌 경우 건축물대장건물명은 제공하지 않습니다.**

```
아리수로93길 40 — 한 자리에 건물 18동
  관리번호 ...0001  대장명=강일리버파크  상세명=308동   시군구용=강일리버파크3단지아파트
  관리번호 ...0003  대장명=강일리버파크  상세명=307동   시군구용=강일리버파크3단지아파트
  관리번호 ...0006  대장명=강일리버파크  상세명=상가동   시군구용=강일리버파크3단지아파트
```

**[전량] 건물 이름 세 칸 중 하나라도 채워진 건물이 전국 1,655,999채다.**

### 4-3. 층·호를 담는 자료가 셋이다

| 자료 | 대상 | 서울 줄 수 |
|---|---|---|
| 상세주소DB (`adrdc_`) | 공동주택이 아닌 건물 | 533,102 |
| 상세주소 표시 · 시군구용 (`rnspbd_adrdc_`) | 위와 사실상 같다 | 533,103 |
| 상세주소 표시 · 건축물대장 (`rnspbt_adrdc_`) | **주로 공동주택** | 3,790,271 |

**[전량 · 서울] 앞 둘은 같은 자료다.** PK 여덟 칸을 전량 대조해 128줄·129줄만 어긋났다. **적재는 시군구용 한 벌만 한다.** 시군구용에는 도로명주소관리번호 칸이 있고 상세주소DB에는 없다.

**[전량 · 서울] 두 계열은 대상이 갈린다.** 시군구용에만 80,790채, 대장에만 136,020채, 양쪽에 301채(0.14%)다. **같은 호를 다르게 부르는 것이 아니라 시군구용이 호를 비워 둔다.**

→ **우선순위를 미리 정하지 않는다.** 양쪽을 한 사전에 넣고 찾은 결과 수로 가른다.

**[전량 · 전국] 상세주소DB의 값 채워짐**

|---|---|
| 줄 수 | 3,238,597 |
| 동명칭 있음 | 150,051 |
| 호접미사 있음 | **128** |
| 층명칭 빈 값 | 1,703,240 |
| 호명칭 빈 값 | 178,001 |
| 호명칭 `비1` | 1,023 |

**324만 중 128건이라 비교에 넣을 실익이 없다.** 「값이 오지 않는다」가 아니라 「실익이 없다」가 제외 근거다.

**동·층·호에 기준 문자가 안 붙는다.**

→ **우리 쪽에도 단위 글자를 붙이지 않는다. 자료형은 문자열이다.** 문자가 섞인 값이 실재하므로 숫자형으로 담을 수 없다. 근거는 `02-data-model.md` 6-3절.

**층명칭에 `null`이라는 글자와 공백 한 칸이 들어온다.**

**[확인 필요] 5층 501~529호를 담은 건물이 있다.** 다가구는 3개 층 이하이므로 다가구가 아니다.

상세주소 부여 대상을 정하는 조문은 주택법을 가리킨다.

**행정안전부 주소기반산업지원서비스 안내**

- 동번호 — 아라비아 숫자 일련번호 또는 한글 (`101동`·`102동` / `가동`·`나동`)
- 층수 — 지상은 일련번호, 지하는 `지하`를 붙인다
- 호수 — `101호`·`102호` / `1호`·`2호` / `지하1호` / `지하101호`
- 표기 — 건물번호와 동·층·호 사이에 쉼표를 쓴다 (`삭주로 89, 201동 101호`)

|---|---|
| 건물번호로 동이 구분되는 경우 | 동번호 |
| 호수에 층수의 의미가 포함된 경우 | 층수 |
| 주거를 목적으로 하는 건물등에서 호수가 중복되지 않는 경우 | 층수 |
| 지하가 한 층인 경우 | 층수에 포함된 숫자 |

제21조④ — 층수를 생략하면 `동`·`호` 표기를 빼고 동번호와 호수를 하이픈으로 잇는다.

**도로명주소법 시행령 제11조의11** — 상세주소 부여 단위

| 단위 | 뜻 |
|---|---|
| 동 | 지상으로 돌출된 형태로 구분되는 단위의 건물등 |
| 층 | 천장과 바닥면으로 구획된 공간 |
| 호 | 하나의 층에서 물리적인 경계로 구분되는 공간 |

**하이픈을 정한 조문은 어디에도 없다.** 시행규칙 제21조④가 하이픈을 언급하지만 층수를 생략한 경우의 표기 방법일 뿐이다.

**그래서 하이픈으로 동·층·호를 판별하지 않는다.**

### 4-7. 상세주소여부 칸의 뜻을 모른다

**[전량] 상세주소여부가 `1`인 건물이 전국 1,088,144채다.** 그런데 상세주소DB에 실제로 줄이 있는 건물은 475,790채다. 반대로 `0`인데 줄이 있는 건물이 5,393채 있다.

**무슨 뜻인지 아직 모른다. 조회 분기에 쓰지 않는다.**

**[전량] 상세주소DB에 나오는 건물 481,183채 중 공동주택은 5,382채(1.1%)다.**

## 7. 참조 캐시 구성

### 캐시는 후보를 좁히는 데만 쓴다

**실재 판정은 DB가 한다.** 실재 확인이 이 설계의 안전장치이므로 캐시가 낡아도 잘못된 확정으로 이어지지 않는다.

| 캐시 오류 | 무슨 일이 생기나 |
|---|---|
| 없어진 도로명을 들고 있다 | 후보로 나와도 실재 확인에서 걸러진다 |
| 새 도로명을 모른다 | 후보 하나를 놓친다 |

두 번째 줄에 예외가 있다. **후보 자체를 만드는 자리는 새 값을 모르면 확인할 대상이 없다.** 역조회 색인, 법정동 사전, 표지 뗀 색인이 그렇다.

### 여섯 층

| 층 | 내용 | 규모 | 어디서 만드나 |
|---|---|---|---|
| 상주 | 앞 세 자리 사전 | 1,677 | `ref.region`의 `stp` 1·2와 읍·면 |
| 상주 | 역조회 색인 (도로명 이름 → 시군구) | 167,217 | `ref.road` + `ref.address` |
| 상주 | 법정동 사전 (지번용) | 10,557 | `ref.region`의 `stp` 3·4 |
| 상주 | **표지 뗀 색인** (열쇠 → 층 + 원래 이름) | 142,576 | `ref.region` + `ref.road` |
| 상주 | **이름 대응 사전** (옛 이름 → 현재 이름) | 초기 0 | `ref.name_map` |
| 지연 | 시군구별 도로명 | 건당 최대 2,388 | 조회할 때 DB에서 올린다 |

**표지 뗀 색인은 표지가 없는 조각을 받는다.** 규칙과 실측은 `03-pipeline.md` 2절 ①-2에 있다.

**이름 대응 사전은 서비스가 도는 동안 찬다.** 처음에는 비어 있고 배치가 견줄 때마다 는다. `03-pipeline.md` 8절에 있다.

**없어진 주소 자리는 `ref.addr_map`이 들고 상주에 올리지 않는다.** 실재 확인이 후보를 다 지운 뒤에만 보므로 상주로 둘 값이 없다. 외부에서 받아 온 답은 `svc.legacy_map`이 든다.

### 상주 사전은 자기를 만든 배치가 끝날 때 갈아 끼운다

**갱신 시점을 사전마다 따로 정하지 않는다.** 사전이 읽는 테이블을 채우는 배치가 끝나면 그 사전을 갈아 끼운다. 사전마다 주기를 두면 규칙이 사전 수만큼 는다.

**통째로 새로 만들어 참조를 바꾼다.** 항목을 하나씩 고치면 반쯤 바뀐 사전으로 판정하는 순간이 생긴다. 무상태 설계라 요청마다 사전을 새로 잡으므로, 도는 중인 요청은 옛 사전을 끝까지 쓴다.

**일 변동분도 받는다.** 후보를 만드는 자리라 새 값을 모르면 그 조각이 사전에 안 걸리고, 조각을 하나도 못 찾은 입력은 관문에서 「주소가 아니다」로 나간다.

**폐지는 지우지 않는다.** 실재 확인이 거른다.

### 7-1. 수동 갱신

**자동만 두면 다음 배치까지 손쓸 방법이 없는 경우가 넷이다.**

| 언제 | 무슨 일이 생기나 |
|---|---|
| 배치가 도중에 죽었다 | `ref`는 새 값인데 사전이 옛 값이다. 다음 날까지 어긋난 채로 답한다 |
| 대응 사전에 내부판정으로 한 줄을 넣었다 | 표에는 들어갔으나 메모리에 안 올라간다 |
| 갈아 끼우기만 실패했다 | 적재는 멀쩡하다. 배치 전체를 다시 돌릴 이유가 없다 |
| 2단계에서 값을 바꿔 가며 잰다 | 사전을 다시 만들 때마다 배치를 통째로 돌릴 수 없다 |

**자동과 수동이 같은 코드를 부른다.**

```
사전 갈아 끼우기
 ├ 배치 끝에서 부른다      자동
 └ 운영 진입점에서 부른다   수동
```

두 경로를 따로 짜면 규칙이 두 벌이 되고 한쪽만 고치는 일이 생긴다. **「갱신 시점을 사전마다 따로 정하지 않는다」와 부딪히지 않는다.** 그 결정은 자동 주기를 말하고, 수동은 주기가 아니라 사람이 부르는 것이다.

**단위는 사전 하나다.** 부를 때 어느 사전인지 지정하고, 지정하지 않으면 전부를 뜻한다. 안 바뀐 사전까지 다시 만들면 시간과 힙을 두 배로 쓴다.

**지켜야 할 것 넷**

| 무엇 | 어떻게 |
|---|---|
| 통째로 만들어 참조를 바꾼다 | 항목을 하나씩 고치지 않는다. 자동과 같다 |
| 만들다 실패하면 옛 사전을 그대로 둔다 | 반쯤 바뀐 사전으로 판정하는 순간을 만들지 않는다 |
| 같은 사전을 동시에 두 번 만들지 않는다 | 도는 중에 또 부르면 「이미 도는 중」을 돌려준다 |
| 갈아 끼운 결과를 지표로 남긴다 | 언제 · 어느 사전 · 몇 건 · 자동인가 수동인가 |

**수동 갱신이 하지 않는 것**

```
사전 갱신     ref  →  메모리 사전        ref는 안 건드린다
적재 재실행   원천 파일  →  ref          다른 배치다
```

`ref`가 낡았으면 사전만 다시 만들어도 옛 값이 그대로 올라온다. 그때 필요한 것은 적재 배치를 다시 부르는 일이고, 「같은 입력을 다시 넣어도 결과가 같아야 한다」가 이미 그것을 받는다.

**지연 적재 층은 갱신 대상이 아니다.** 수동으로는 「비운다」만 있으면 된다.

**진입점은 정제 API와 갈라 둔다.** 인증과 호출 한도는 앞단이 맡는다는 결정이 여기에도 걸린다. 이 애플리케이션은 검증이 끝난 호출을 받아 사전을 다시 만들 뿐이다. **운영 진입점 넷은 14-6절에 모아 두었다.**

### 지연 적재 층에는 갱신 로직이 없다

고치지 않고 버린다. 다시 조회하면 DB에서 최신 값이 올라온다.

### 법정동 사전

|---|---|---|
| 법정읍면동 (`stp` 3) | 상위 시군구의 법정동코드 + 이름 | 자기 법정동코드 |

## 8. 갱신 서비스 흐름

**설계가 정하는 것과 구현이 정하는 것을 가른다.**

| 설계가 정한다 | 구현이 정한다 |
|---|---|
| 배치가 몇 개이고 언제 도는가 | SQL로 판단할지 애플리케이션 코드로 판단할지 |
| 각 배치가 무엇을 보고 갈라지는가 | 문장 형태 · 커밋 단위 · 배치 프레임워크 |
| 실패했을 때 다시 돌릴 수 있는가 | 병렬 처리 여부 |
| 무엇을 지표로 남기는가 | |
| 순서에 매인 자리가 어디인가 | |

### 8-0. 배치 셋

```
[한 번]      월 전체분          →  ① 최초 적재  →  ref 전량 · 파생 생성
[매일]       일 변동분          →  ② 일 반영    →  폐지 판단 · 대응 비교 · 반영 · 파생 재구성
[매월]       월 전체분          →  ③ 월 대사    →  전체분을 정답으로 맞춘다 · 대응 비교
```

**대응 비교는 별도 배치가 아니라 ②와 ③ 안의 한 마디다.** 덮어쓰기 직전에 전후를 견주므로 그 자리에서만 돌 수 있다.

**배치에 파일을 넘기는 자리는 적재 진입점이다.** 받는 것과 남기는 것은 14절에, 진입점 자체는 14-6절에 있다.

### 8-1. ① 최초 적재 — 한 번

*받는 것* — **월 전체분. 자료 열 중 일곱만 적재한다.**

| 안 넣는 자료 | 왜 |
|---|---|
| 관련지번 (건물DB) `jibun_` | 한글 쪽과 같은 자료다. 전량 대조로 확인했다 |
| 도로명 `TN_SPRD_RDNM` | 고유 칸 넷(부여사유 · 도로구간 기초번호 둘 · 효력발생일)을 안 담기로 했다. 나머지는 도로명코드가 준다 |
| 상세주소DB `adrdc_` | 시군구용과 사실상 같은 자료다. 시군구용에는 도로명주소관리번호 칸이 있고 여기에는 없다 |

*판단* — **없다.** 전체분에는 사유코드가 오지 않는다 (전량 확인)

*대응 비교* — **돌지 않는다.** 견줄 이전 스냅숏이 없다. `ref.name_map`과 `ref.addr_map`은 비어 있는 채로 시작한다

*순서를 묶는 제약 셋*

| 제약 | 어디 | 내용 |
|---|---|---|
| 짝지어 읽는다 | `ref.building` | 건물정보에 도로명주소관리번호 칸이 없다. 상세주소 동 표시가 그 값을 준다 |
| 두 자료가 행을 나눠 갖는다 | `ref.lot` | 대표지번은 건물정보 안에, 나머지는 관련지번에 있다. 81.2% 대 18.8% |
| 파생은 맨 뒤 | `ref.unit_lookup` · `ref.token` | 재료가 되는 마스터가 다 들어와야 만든다 |

**`ref`에 외래키를 걸지 않으므로 마스터끼리는 순서가 자유롭다.** 위 셋 말고 순서에 매인 자리가 없다.

**순서를 케이스로 적지 않고 제약으로 적는다.** 자료가 하나 늘면 순서표를 다시 짜는 것이 아니라 그 자료가 위 셋 중 어디에 걸리는지만 본다.

*마디가 둘이다*

**원천 복원이 먼저 돌고 엔진 전환이 뒤에 돈다.** 파일을 읽어 원천 구조 그대로 `stg` 스테이징 테이블에 넣은 뒤, 그것을 재해석해 `ref`를 만든다. **스테이징은 배치가 도는 동안만 존재하고 영구 스키마로 남지 않는다.** 근거는 `decisions.md` 1-3-20절에 있다.

**나눈 이유는 실패하는 자리가 다르기 때문이다.** 원천 복원은 파일이 깨졌을 때 실패하고, 엔진 전환은 재해석 규칙이 틀렸을 때 실패한다. 한 마디로 묶으면 어느 쪽에서 틀렸는지 가릴 수 없다.

**아래 순서는 엔진 전환 마디의 순서다.** 원천 복원은 자료 일곱을 아무 순서로나 넣어도 된다. 파일과 테이블이 하나씩 맞고 서로를 참조하지 않는다.

*순서*

```
마스터
  1  ref.region       도로명주소 한글       최하위 행만 온다. 상위 행은 뒷자리를 0으로 채워 만든다
  2  ref.road         도로명코드            읍면동 칸이 빈 줄. 전국분이라 지역 필터를 건다
  2  ref.road_emd     도로명코드            읍면동 칸이 찬 줄. 같은 파일을 조건으로 가른다
  3  ref.address      도로명주소 한글
  4  ref.address_lot  관련지번 (한글 쪽)
  5  ref.lot          건물정보 + 관련지번   양쪽에서 받아 넷(법정동코드·산여부·본번·부번)으로 중복을 없앤다
  6  ref.building     건물정보 + 동 표시    동 표시가 도로명주소관리번호를 채운다
  7  ref.unit         상세주소 표시 두 벌   시군구용은 출처 S, 건축물대장은 출처 L

파생
  8  ref.unit_lookup  3 + 6 + 7
  9  ref.token        1 + 2 + 6
```

*6번에서 주소자리를 못 채우는 건물이 있다* — **서울 230채다.** 잠실역 실내 도로명에 붙은 건물이 건물정보에는 있고 동 표시·도로명주소 한글에는 없다. **비운 채로 넣는다.** 근거는 `02-data-model.md` 6-4절 `ref.building`.

*상주 사전* — **배치가 끝난 뒤 다섯을 다 만든다.** 앞 세 자리 사전과 법정동 사전은 1번이, 역조회 색인은 2·3번이, 표지 뗀 색인은 1·2번이 재료다. 이름 대응 사전은 비어 있다

*실패하면* — 처음부터 다시 돌린다. 비우고 넣는 것이 대사보다 싸다

*지표* — 자료별 적재 줄 수, **6번에서 주소자리를 못 채운 건물 수.** 서울에서 230을 크게 벗어나면 동 표시를 덜 읽은 것이다. **줄 수는 적재 장부의 파일 줄이 든다** (14-6절)

### 8-2. ② 일 반영 — 매일

*받는 것* — 일 변동분 파일

*판단* — **줄마다 「폐지인가」 하나뿐이다.**

```
폐지다      →  자료별 처리        건물·도로명은 남기고 표시, 관련지번·상세위치는 지운다
아니다      →  대응 비교 → 현재 값으로 만든다   신규와 변경을 가르지 않는다
어느 쪽이든  →  건드린 주소 자리를 모아 둔다
```

**폐지를 아는 방법이 자료마다 다르다.**

| 자료 | 무엇으로 아나 |
|---|---|
| 도로명 · 도로명코드 | **사용여부 = 1.** 별도 칸이 있다 |
| 건물 · 주소자리 · 관련지번 · 상세위치 | **이동사유코드 = 63.** 사용여부 칸이 없다 |

*대응 비교* — **덮어쓰기 직전에 돈다.** 8-6절에 있다

*마지막 마디* — 모아 둔 주소 자리만 파생 테이블에서 지우고 다시 만든다. **[전량] 7월 기준 15,361곳이고 서울 상세주소 4,323,373줄 중 38,541줄(0.89%)을 다시 쓴다**

*실패하면* — **처리한 자리를 기록하며 자리 단위로 커밋한다.** 죽은 지점부터 이어 돌린다

*지표* — 사유코드별 건수, 삭제·삽입 건수, **새로 만든 대응 줄 수.** 평소 폭을 벗어나면 멈춘다

*역조회 색인* — **신규만 넣는다.** 폐지·변경은 반영하지 않는다. 후보로 나와도 실재 확인이 거른다

*앞 세 자리 사전 · 법정동 사전 · 표지 뗀 색인* — **`ref.region` 또는 `ref.road`가 바뀐 날만 다시 만든다.** 통째로 새로 만들어 참조를 바꾼다

*이름 대응 사전* — **`ref.name_map`에 줄이 는 날만 다시 만든다**

### 8-3. ③ 월 대사 — 매월

*하는 일* — 전체분을 정답으로 보고 우리 것과 맞춘다

```
전체분에만 있음   → 넣는다
현재 값에만 있음  → 뺀다
값이 다름         → 대응 비교 → 전체분 값으로 맞춘다
```

*판단* — **두지 않는다.** 세 갈래 모두 전체분을 따른다. 근거는 팀프레시 장애 대응 경험이다. 일 변동분에 없고 월 전체분에 있는 주소는 전체분 쪽이 맞았다

*왜 있는가* — **일 변동분을 하루라도 놓치면 그 뒤로 계속 어긋난 채 간다.** 대사가 그것을 되돌린다. 일 반영이 완벽하다는 전제를 세우지 않는 장치다

*지표* — **어긋난 건수 자체가 지표다.** 0에서 멀어지면 일 반영에 구멍이 있다는 뜻이다

*상주 사전* — **다섯 다 새로 만들어 통째로 갈아 끼운다**

### 8-4. 셋을 관통하는 요구 — 다시 돌려도 같은 결과

**같은 입력을 다시 넣어도 결과가 같아야 한다.**

배치는 죽는다. 파일이 두 번 들어오기도 한다. 다시 돌렸을 때 값이 달라지면 어디까지 돌았는지를 사람이 추적해야 하고, 그때부터 운영이 사람 손에 매인다.

**이 요구가 「신규와 변경을 가르지 않는다」를 낳았다.** 신규를 넣기로만 처리하면 두 번째 실행에서 키 충돌로 멈춘다. 「현재 값으로 만든다」로 두면 몇 번을 돌려도 같다.

**대응 비교도 같은 성질을 지킨다.** 같은 두 스냅숏을 다시 견주면 같은 대응이 나오고, 이미 있는 줄은 덮어쓴다.

**상주 사전도 같다.** 통째로 다시 만드므로 몇 번을 돌려도 같은 사전이 나온다.

**적재 진입점도 같다.** 같은 폴더를 두 번 넣어도 결과가 같아야 한다. 14-6절에 있다.

**구현이 SQL이든 애플리케이션 코드든 이 성질을 만족해야 한다.**

### 8-5. 사유코드는 표로 쌓지 않는다

②가 사유코드를 읽지만 **읽은 값을 표로 쌓지 않는다.** 갈래를 가르는 데만 쓰고 버린다.

**원천 이력이 「무엇이 무엇으로 바뀌었나」를 안 준다.** 도로명 폐지 71줄의 변경이력정보가 전부 비어 있고, 변경이력사유 `0`(도로명변경)이 전체분에도 변동분에도 없다 (12-3절).

**그래서 원천 이력을 옮겨 담는 표는 만들지 않는다.** 대신 우리가 전후를 견줘 대응을 만든다. 아래 8-6절이 그 자리다.

**남기는 것은 지표다.** 사유코드별 건수, 삭제·삽입 건수, 새로 만든 대응 줄 수를 배치 실행 기록으로 남긴다.

### 8-6. 대응 비교 — 갱신 전후를 견준다

**설계 전체는 `03-pipeline.md` 8절에 있다.** 여기서는 배치 안의 자리만 적는다.

*재료* — **건물관리번호 하나다.** 주소가 바뀌어도 안 바뀌고, 행정구역 개편도 건넌다. 도로명코드와 법정동코드는 개편에서 함께 재채번되므로 열쇠로 쓰지 않는다 (3-4절)

*도는 자리* — **덮어쓰기 직전이다.** ②와 ③ 안에서 「현재 값으로 만든다」 바로 앞에 선다. 덮은 뒤에는 견줄 옛 값이 없다

*견주는 것* — **같은 건물관리번호의 주소 전후다.** 한 번 견주면 이름 대응과 자리 대응이 함께 나온다

| 달라진 곳 | 어디로 |
|---|---|
| 시도 · 시군구 · 읍면동 이름 | `ref.name_map` |
| 도로명 이름 | `ref.name_map` |
| 도로명주소관리번호 | `ref.addr_map` |

*입력을 스냅숏 둘로 정의한다*

```
비교 배치
  입력   이전 스냅숏 · 새 스냅숏
  일     같은 건물관리번호끼리 이름과 자리를 견준다
  출력   달라진 것마다 대응 한 줄
```

| 부르는 자리 | 이전 스냅숏 | 새 스냅숏 | 출처 칸 |
|---|---|---|---|
| ② 일 반영 · ③ 월 대사 | 현재 `ref` | 스테이징에 올린 새 자료 | 배치비교 |
| 과거분을 넣을 때 | 스테이징에 올린 과거 전체분 | 현재 `ref` | 과거연동 |

**어디서 온 두 벌인지 배치가 묻지 않는다.** 그래서 2024년 8월 전체분을 스테이징에 올리고 한 번 더 부르면 전남광주통합특별시와 인천 개편 대응이 통째로 들어온다. **새 코드를 짜지 않는다.**

*한 옛 이름이 현재 이름 여럿으로 갈릴 수 있다* — 인천 서구가 서해구와 검단구로 나뉜다. 줄을 여럿 만들고 조회에서 `EXACT`/`MANY`로 낸다

*과거연동의 한계* — 두 시점만 견주므로 그 사이에 두 번 바뀐 것은 한 번으로 보인다. **출처 칸이 그것을 남긴다**

*실패하면* — 대응 줄은 덮어쓰기이므로 다시 돌려도 같다. 이어 돌린다

*지표* — 새로 만든 대응 줄 수. 평소 폭을 크게 벗어나면 이전 스냅숏을 잘못 잡은 것이다

## 9. 지번 표기 규칙

**원천에 주소 표기 문자열이 없다.** 어느 파일도 「서울특별시 종로구 자하문로 94」를 그대로 주지 않는다.

**그래서 표기 규칙은 자료에서 역산할 수 없다.** 사람이 친 문자열을 어떻게 칸으로 나눌지는 법령에서 가져온다.

### 근거 조문

근거는 「공간정보의 구축 및 관리 등에 관한 법률」과 그 시행령이다.

| 무엇 | 조문 | 내용 |
|---|---|---|
| 지번의 정의 | 법 제2조 22호 | 필지에 부여해 지적공부에 등록한 번호다 |
| 동·리가 앞에 온다 | 법 제2조 23호 | 지번부여지역은 동·리 또는 이에 준하는 지역이다 |
| 임야 표시 | 시행령 제56조① | 임야대장·임야도에 등록하는 토지는 숫자 앞에 `산`을 붙인다 |
| 본번과 부번 | 시행령 제56조② | 둘 사이를 `-`로 잇는다. 이 표시는 「의」라고 읽는다 |

**「의」로 읽는다는 것이 실무에 걸린다.** 「150의 3」으로 치는 입력이 조문상 근거가 있는 표기다.

### 「이에 준하는 지역」은 `가`다

**[전량 · 전국] 법정읍면동 3,589 · 법정리 6,968**

| 끝 글자 | 개수 |
|---|---|
| `동` | 2,079 |
| `면` | 1,006 |
| `가` | 266 |
| `읍` | 236 |
| `로` | 2 |

리는 전량 `리`로 끝난다. 한자를 괄호로 병기한 리가 6개 있다.

`가`로 끝나는 것이 「이에 준하는 지역」이다.

**[전량 · 전국] 도로명과 법정동·리 이름이 겹치는 것은 둘이다.** `남성로`와 `세종로`다.

| 23 | **폴더 이름과 파일 이름이 연월·구분·자료·시도를 이미 든다** | 사람이 목록을 적지 않는다. 적재 진입점이 경로를 읽는다 |

## 12. 변경 이력 — 무엇이 채워지고 무엇이 안 채워지나

### 12-1. 말소일자는 안 온다

| 자료 | 사용여부 | 말소일자 |
|---|---|---|
| 도로명코드 전체분 (371,958줄) | **전량 `0`** | **전량 빈 값** |
| 도로명 전체분 (371,921줄) | **전량 `0`** | **전량 빈 값** |
| 도로명코드 변동분 (434줄) | `0` 363 / `1` 71 | 전량 빈 값 |
| 도로명 변동분 (541줄) | `0` 470 / `1` 71 | 전량 빈 값 |

**쓸 수 없는 칸이다.**

**줄 끝 `\r`를 떼지 않으면 마지막 칸이 채워진 것으로 잘못 세어진다.**

### 12-2. 없어진 도로명은 변동분에만 나타난다

전체분은 살아 있는 도로명의 스냅숏이라 사용여부가 전부 `0`이다. 변동분에는 그달에 없어진 것이 사용여부 `1`로 71건 들어 있다. **그달 한 번뿐이고 다음 달에는 없다.**

**전체분 두 벌을 견주면 같은 것이 나온다.** 6월↔7월에서 6월에만 있는 열쇠 71개와 7월에만 있는 열쇠 363개가 나왔다. 4-8절에 있다.

### 12-3. 폐지 건에는 대응 관계가 없다

| 자료 | 변경이력사유 | 변경이력정보 |
|---|---|---|
| 도로명코드 변동분 | 빈값 363 / `1` 폐지 71 | 「신규」 363 / **빈값 71** |
| 도로명 변동분 | 빈값 363 / `9` 기타 107 / `1` 폐지 71 | 「신규」 363 / 빈값 178 |

**없어진 71건은 변경이력정보가 전부 비어 있다.**

**변경이력사유 `0`(도로명변경)이 전체분에도 변동분에도 한 건이 없다.**

**이것이 원천 이력을 옮겨 담지 않는 근거다.** 다만 대응 자체를 포기하는 근거는 아니다. 건물관리번호가 개편을 건너므로 갱신 전후를 견주면 대응이 나온다. 8-6절에 있다.

### 12-4. 이전도로명주소도 안 온다

도로명주소 한글의 18번 칸이다. **전체분 16개 시도와 변동분 9,785줄이 전부 빈 값이다.**

## 14. 원천 자료를 어떻게 받고 무엇만 남기나

**연계 API는 기관 신청만 받는다.** 개인은 주소기반산업지원서비스 화면에서 내려받는다 — 홈 > 주소정보 자료제공 > 주소정보 다운로드. **그래서 이 설계는 파일을 입력으로 삼는다.** 배치의 입력이 이미 「스테이징에 올린 두 벌」로 정의돼 있어(`03-pipeline.md` 8-5절) 받는 방법이 바뀌어도 배치는 안 바뀐다.

### 14-1. 묶음 여섯 중 넷을 받는다

| 묶음 | 받나 | 왜 |
|---|---|---|
| 건물DB | **받는다** | 건물정보와 도로명코드가 여기 있다 |
| 도로명주소 한글 | **받는다** | 주소자리와 관련지번 |
| 상세주소 표시 | **받는다** | 시군구용과 건축물대장 두 벌 |
| 상세주소 동 표시 | **받는다** | 건물의 도로명주소관리번호를 준다 |
| 주소DB | 안 받는다 | 건물DB 갈래를 골랐다. 안에 든 `개선_도로명코드_전체분.txt`는 17칸이라 우리가 쓰는 20칸 `road_code`와 다른 파일이다 |
| 상세주소DB | 안 받는다 | 시군구용과 같은 자료이고 도로명주소관리번호 칸이 없다 |

### 14-2. 압축을 푼 뒤 남기는 파일

| 자료 폴더 | 전체분 | 변동분 | 적재 대상 |
|---|---|---|---|
| `building-db` | `build_{시도}.txt` | `build_mod.txt` | 건물정보 |
| `building-db` | `road_code_total.txt` | `road_code_mod.txt` | 도로명코드 |
| `road-address-kor` | `rnaddrkor_{시도}.txt` | `rnaddrkor_mod.txt` | 도로명주소 한글 |
| `road-address-kor` | `jibun_rnaddrkor_{시도}.txt` | `jibun_rnaddrkor_mod.txt` | 관련지번 |
| `detail-address-display` | `rnspbd_adrdc_{시도}.txt` | `rnspbd_adrdc_mod.txt` | 상세주소 표시 시군구용 |
| `detail-address-display` | `rnspbt_adrdc_{시도}.txt` | `rnspbt_adrdc_mod.txt` | 상세주소 표시 건축물대장 |
| `detail-address-dong` | `rnspbd_dong_{시도}.txt` | `rnspbd_dong_mod.txt` | 상세주소 동 표시 |

**버리는 파일은 `jibun_{시도}.txt`뿐이다.** 건물DB 안에 있고 도로명주소 한글 쪽 `jibun_rnaddrkor_*`와 같은 자료다. 이름이 닮아 묶음째 지우는 방식으로는 안 걸린다.

`[가이드]*.pdf`와 `[자료건수]*.txt`는 적재 대상이 아니나 근거 자료라 남긴다.

**성질 둘을 진입점이 알아야 한다.** `road_code_total.txt`는 전국 한 벌이라 시도로 안 갈린다. 변동분은 자료마다 `_mod.txt` 하나이고 역시 전국 한 벌이다.

### 14-3. 폴더 규약 — 한 층이 사실 하나만 든다

```
{연-월}_source / {구분} / {자료} / {원천 파일명}
2026-07_source / full   / building-db / build_seoul.txt
```

| 층 | 값 | 무엇을 정하나 |
|---|---|---|
| 연-월 | `2024-08` · `2026-06` · `2026-07` | 어느 달 배포인가 |
| 구분 | `full` · `changes` | 전체분인가 변동분인가 |
| 자료 | 위 네 폴더 | 어느 묶음인가 |
| 파일명 | 원천 그대로 | 어느 자료이고 어느 시도인가 |

**원천이 준 폴더 이름을 그대로 쓰지 않는다.** 잎에 연월과 구분이 되풀이돼 같은 값을 두 번 읽게 된다.

**파일명은 원천 그대로 둔다.** 자료와 시도를 이미 들고, 고치면 가이드 문서와 대조가 끊긴다.

### 14-4. 받는 범위

| 무엇 | 왜 |
|---|---|
| 2024-08 전체분 | 과거연동. 개편 전 이름을 든 유일한 벌이다. 건물DB 묶음만 있으면 된다 |
| 2026-06 전체분 | 개편이 시행 전에 반영된다는 것을 확인한 벌이다 |
| 2026-07 전체분 | 최초 적재의 정답 |
| 2026-07 변동분 | 일 반영 배치를 시험할 재료 |

**2026-06 변동분은 안 받는다.** 전체분 두 벌을 견주면 그 사이에 바뀐 것이 다 나온다. 4-8절에서 확인했다.

### 14-5. 왜 한 달 전 벌로는 안 되는가

**[전량] 2026년 6월 30일 기준 자료에 이미 전남광주통합특별시가 있다.** 시도 열여섯이 7월과 같고, 6월↔7월에서 이름이 바뀐 것이 시도·시군구·읍면동·도로명 모두 0건이다.

**두 벌이 서로 다른 시점인 것은 맞다.** 고시일자 최댓값이 6월분은 `20260630`, 7월분은 `20260731`이다. 줄 수도 371,666과 371,958로 다르다.

→ **행정안전부가 시행 전에 미리 담는다.** 며칠 앞서 담는지는 안 쟀다.

### 14-6. 적재 진입점

**파일에서 스테이징까지의 한 마디를 이 절이 맡는다.** 그 뒤는 8절의 배치 셋이 받는다.

#### 받는 것 둘

| 무엇 | 값 |
|---|---|
| 폴더 | `{연-월}_source/{구분}` 한 층 |
| 배치 종류 | 최초적재 · 일반영 · 월대사 · 과거연동 |

**폴더만으로는 모자란다.** 최초 적재·월 대사·과거연동이 전부 `full` 폴더를 받고, 과거연동은 대응 비교의 스냅숏 방향까지 뒤집는다(8-6절). **경로가 드는 사실은 연월과 구분뿐이고 「무슨 배치인가」는 거기 없다.**

**목록이 아니라 값 하나다.** 「사람이 목록을 적지 않는다」와 부딪히지 않는다.

**구분 층을 받는 이유는 한 실행이 전체분이거나 변동분이지 둘 다가 아니기 때문이다.** 이 두 층을 받으면 연월과 구분을 경로에서 읽고 자료와 시도를 그 아래에서 읽는다.

**구분과 배치 종류가 어긋나면 멈춘다.** `changes` 폴더에 최초 적재를 부르는 것이 그 자리다.

#### 파일을 고르는 규칙 — 자료 폴더와 접두어를 짝으로 맞춘다

접두어만 보면 두 자리에서 걸린다. `jibun_`은 버리고 `jibun_rnaddrkor_`는 적재하며, `rnspbd_adrdc_`와 `rnspbd_dong_`은 앞 일곱 글자가 같다.

**두 값이 짝을 이루면 특례가 필요 없다.** 버리는 `jibun_`은 `building-db`에 있고 적재하는 `jibun_rnaddrkor_`는 `road-address-kor`에 있으므로, 자료 폴더마다 접두어 목록을 따로 두면 어느 쪽도 남의 목록에 걸리지 않는다.

| 자료 폴더 | 접두어 |
|---|---|
| `building-db` | `build_` · `road_code_` |
| `road-address-kor` | `rnaddrkor_` · `jibun_rnaddrkor_` |
| `detail-address-display` | `rnspbd_adrdc_` · `rnspbt_adrdc_` |
| `detail-address-dong` | `rnspbd_dong_` |

**접두어를 떼고 남는 값이 시도다.** 예외는 14-2절이 적어 둔 원천 성질 둘이다. 구분이 `changes`면 남는 값이 `mod` 하나이고 전국 한 벌이며, 구분이 `full`이고 남는 값이 `total`이면 도로명코드의 전국 한 벌이다.

**검사는 「있어야 할 것이 있는가」로 한다.** 접두어 일곱마다 파일이 한 개 이상 있는지만 본다. **시도 수를 못박지 않는다.** 서울만 받은 폴더도 정상이고, 과거연동은 건물DB 묶음만 있으면 된다.

**모르는 파일은 건너뛰고 이름을 지표에 남긴다. 멈추지 않는다.** 원천이 파일을 하나 더 얹었다고 그날 운영이 깨지면 안 되고, 「자료마다 담는 범위가 다른 것이 정상이다」가 여기에도 걸린다. **멈추는 것은 반대쪽이다** — 적재 대상인데 파일이 없는 경우다.

#### 적재 장부 — 표 둘

**한 표에 담으면 배치 종류·연월·구분이 파일 줄마다 되풀이돼 제3정규형을 깬다.** 실행이 끝난 시각을 적을 때 서울 일곱 줄, 전국이면 아흔일곱 줄을 함께 고쳐야 하고, 하나를 놓치면 같은 실행이 두 시각을 든다. **폴더가 비면 파일 줄이 없어 「불렀으나 아무것도 못 골랐다」가 아예 안 남는다.**

| 표 | 한 줄이 무엇인가 | 논리명 |
|---|---|---|
| `svc.load_run` | 실행 하나 | 적재실행 |
| `svc.load_file` | 파일 하나 | 적재파일 |

**칼럼은 `02-data-model.md` 6-4절에 있다.**

**파일 줄의 열쇠는 적재실행식별자와 원천파일명이다.** 건너뛴 파일은 자료와 시도를 못 채우므로 그 둘을 열쇠로 쓸 수 없다. 파일명은 폴더 안에서 유일하고 원천 그대로 두기로 이미 정해 둔 값이다.

**자리는 `svc`다.** 스키마를 가른 근거가 「온라인이 참조 마스터를 고칠 길을 권한으로 막는다」인데, 장부는 배치만 쓰고 온라인은 안 읽는다. `ref`는 원천에서 나온 참조 자료를 담는 자리라 성격이 다르고, 표 둘 때문에 스키마를 넷으로 늘리는 것은 값을 못 한다.

**장부는 판단에 끼지 않는다.** 적재가 「현재 값으로 만든다」이므로 같은 폴더를 두 번 넣어도 결과가 같다(8-4절). 장부를 보고 이미 넣은 파일을 건너뛰게 만들면 장부가 틀렸을 때 적재가 함께 틀린다. **죽은 지점부터 이어 돌리는 일은 8-2절의 자리 단위 커밋이 맡는다.**

#### 운영 진입점 넷

| 진입점 | 하는 일 |
|---|---|
| 적재 | 폴더와 배치 종류를 받아 배치를 돈다 |
| 사전 갈아 끼우기 | 상주 사전을 통째로 다시 만든다. 자동과 같은 코드다 (7-1절) |
| 지연 적재 층 비우기 | 고치지 않고 버린다 (7-1절) |
| 진행 상태 보기 | 장부를 읽어 도는 중인지, 마지막 실행이 언제인지 낸다 |

**넷이 규칙 셋을 함께 지킨다.**

- **정제 API와 갈라 둔다.** 인증과 호출 한도는 앞단이 맡는다
- **도는 중에 또 부르면 「이미 도는 중」을 돌려준다.** 실행 장부의 실행결과 칸이 그 값을 든다
- **부른 결과를 지표로 남긴다**

### 표본 만들기 — 주의점

**`awk`에 한글 값을 비교시키려면 `iconv`를 먼저 돌린다.** 파이프 순서를 바꾸면 `awk`가 MS949 바이트를 못 읽는다. 키가 숫자뿐이면 변환 없이 그대로 비교해도 된다.

**활용가이드 PDF는 실제로 PDF가 아니다.** 쪽마다 JPEG와 텍스트를 담은 zip이고 확장자만 `.pdf`다.

**`iconv`가 없는 환경이 있다.** 그럴 때는 파이썬에서 `open(p, encoding='cp949', errors='replace')`로 읽는다.
