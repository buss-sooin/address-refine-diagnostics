# 설계7 — 인터페이스 정의서

**답하는 질문: 이 구조가 무슨 규칙에서 나왔고 책임을 어떻게 나눴는가**

대상은 정제 코어와 API 서비스다. 짝이 되는 그림은 `component-uml.drawio`이고, 흐름 서술은 `03-pipeline.md`에 있다.
이 문서는 새 결정을 담지 않는다. 설계 문서에 흩어져 있던 규칙을 「그 규칙을 지키는 구조는 무엇인가」로 다시 읽은 결과다.

**자바 타입 이름은 후보다.** 확정은 구현 단계에서 한다.

---

## 1. 용어

기술 용어는 외래어 표기로 적고 원어를 병기한다.

| 말 | 원어 | 비고 |
|---|---|---|
| 스트래티지 패턴 | Strategy | 업무 용어 '전략'(교정 전략·검출 전략)과 겹치므로 패턴 쪽은 외래어로 적어 가른다 |
| 컴포지트 패턴 | Composite | |
| 템플릿 메서드 패턴 | Template Method | |
| 컨텍스트 객체 | Context | |
| 포트와 어댑터 | Ports and Adapters | 헥사고날 아키텍처라고도 한다 |
| 리절트 객체 | Result | GoF 목록에 없는 관용 기법이다 |
| 오케스트레이터 | Orchestrator | 단계를 차례로 부르는 자리 |

---

## 2. 원칙 4가지

구조를 정한 것은 취향이 아니라 아래 네 규칙이다.

| # | 원칙 | 어디서 왔나 |
|---|---|---|
| 1 | **실패는 예외가 아니라 값이다** | 파는 것이 정제된 주소가 아니라 행동 가능한 실패 사유다 (`01-scope.md` 1절) |
| 2 | **순서를 아는 자리는 하나다** | 지번 뒤에 도로명이 오는 되돌아옴이 있고, 갈래가 앞으로 늘어난다 (`03-pipeline.md` 상태 전이표) |
| 3 | **경우를 나열하지 않고 규칙으로 짠다** | 정규식을 케이스마다 덧붙이던 방식을 없애려는 것이 이 프로젝트다 |
| 4 | **바깥은 포트 뒤에 둔다** | 카카오를 갈아끼울 수 있어야 한다 (`01-scope.md` 4절) |

## 3. 패턴 6가지

| 패턴 | 적용 자리 | 의도 | 근거 규칙 | 어긋난 모습 |
|---|---|---|---|---|
| 리절트 객체 | 모든 단계의 반환 | 실패를 값으로 내야 사유를 판다 | 원칙 1 | 못 찾으면 예외를 던지고 받는 쪽에 "실패"만 남는다 |
| 스트래티지 | 응답 조립기 | 처리는 하나로 두고 반환 모양만 소비자에 맞춘다 | 두 반환 value를 같은 모양으로 맞추지 않는다 | 반환 타입이 하나이고 안에 「교정이면」 분기가 생긴다 |
| 템플릿 메서드 | 정제 오케스트레이터 | 순서를 한 곳에 두어 단계를 건너뛸 수 없게 한다 | ③단계 실재 확인을 건너뛰지 않는다 | 단계가 다음 단계를 직접 부른다 |
| 컨텍스트 객체 | 정제 컨텍스트 | 단계가 서로를 모른 채 값을 이어 나른다 | 버린 조각을 감추지 않는다 · 무상태 | 버린 조각이 지역 변수로 사라진다 |
| 컴포지트 | 갈래 셋 | 갈래를 다 돌려야 교집합이 나온다 | 갈래에 우선순위를 두지 않는다 | 갈래 하나를 골라 부른다 |
| 포트와 어댑터 | 자원 포트 넷 | 바깥이 바뀌어도 코어를 고치지 않는다 | 원칙 4 | 코어가 카카오를 직접 부른다 |

### 같은 모양인데 뜻이 반대인 두 자리

갈래 셋과 후보 검색기는 둘 다 「인터페이스 하나에 구현 여럿」이다. 쓰는 방식이 정반대다.

| | 갈래 셋 | 후보 검색기 |
|---|---|---|
| 구현을 어떻게 쓰나 | 전부 실행하고 합친다 | 하나를 골라 그것만 쓴다 |
| 패턴 | 컴포지트 | 스트래티지 |
| 자바에서 | 구현을 목록으로 주입받는다 | 구현 하나를 주입받는다 |
| 근거 | 「갈래에 우선순위를 두지 않는다」 | 「다른 검색 방법을 더할 때는 하나 더 만들어 바꿔 쓴다」 |

뭉쳐서 「인터페이스와 구현」으로만 적으면 갈래에서 하나만 고르는 코드가 나온다. 그러면 교집합을 못 만든다.

## 4. 인터페이스 15개

### 4-1. 단계 8개 — 정제 오케스트레이터만 부른다

| # | 이름 | 자바 이름 후보 | 컨텍스트에서 읽는 것 | 컨텍스트에 적는 것 |
|---|---|---|---|---|
| ① | 파서 | `AddressParser` | 원문 · 우편번호 · 전략 value | 조각 목록 · 고쳐 읽은 자리 |
| ② | 관문 | `AddressGate` | 조각 목록 | 주소 여부 |
| ③ | 표기 가르기 | `NotationClassifier` | 조각 목록 | 성립하는 표기 집합 |
| ④ | 갈래 | `AddressBranch` | 조각 목록 · 전략 value · 좁힌 범위 | 갈래별 후보 집합 · 층 결과 |
| ⑤ | 행정동 판정 | `AdminDongJudge` | 조각 목록 | 사유 |
| ⑥ | 합치기 | `CandidateMerger` | 갈래별 후보 집합 | 건물 후보 집합 · 버린 조각 목록 |
| ⑦ | 실재 확인 | `ExistenceVerifier` | 건물 후보 · 상세 조각 · 전략 value | 살아남은 후보 · 상세 확정 수준 |
| ⑧ | 응답 판정기 | `ResultGrader` | 후보 · 버린 조각 · 상세 확정 수준 · 전략 value | 등급 · 사유 |

**책임과 하지 않는 일**

| # | 책임 | 하지 않는 일 |
|---|---|---|
| ① | 단위 표기 글자로 끊고 사전에서 찾는다 | 옳고 그름을 정하지 않는다. 좁힌 범위의 후보 목록을 만들지 않는다 |
| ② | 주소로 볼 만한 입력인지 가른다 | 옳은 주소인지 묻지 않는다. 단위 표기가 있는지로 판단하지 않는다 |
| ③ | 성립하는 표기를 전부 표시한다 | 넷 중 하나를 고르지 않는다 |
| ④ | 후보 집합을 만든다 | 건물을 하나로 정하지 않는다 |
| ⑤ | 행정동으로 쓰였다는 사실과 사유를 만든다 | 찾지 않는다. 실재 확인을 거치지 않는다 |
| ⑥ | 건물 단위로 맞춰 교집합 또는 합집합을 낸다 | 갈래에 우선순위를 두지 않는다 |
| ⑦ | DB에 있는 것만 남긴다 | 닮은 정도로 순위를 매기지 않는다 |
| ⑧ | 등급과 사유를 각각 센다 | 하나로 좁혀졌다고 버린 조각을 감추지 않는다 |

**갈래 셋은 같은 약속의 구현이다.** `RoadBranch` · `LotBranch` · `BuildingNameBranch`가 받고 내는 모양이 같고 안이 다르다.

### 4-2. 판정 부품 2개 — 여러 단계가 함께 부른다

| 이름 | 자바 이름 후보 | 부르는 쪽 | 받는 값 | 돌려주는 값 |
|---|---|---|---|---|
| 층 판정기 | `LevelJudge` | 파서 · 도로명 갈래 · 건물이름 갈래 | 조각 · 층 이름 · 허용 오타 | 층 결과 두 값 |
| 후보 검색기 | `DictionarySearcher` | 층 판정기 | 조각 · 층 이름 | 후보 목록. 후보마다 닮은 정도 |

**지번 갈래는 층 판정기를 부르지 않는다.** 건물번호와 지번은 정확 일치이고 닮은 정도를 재지 않는다.

### 4-3. 자원 포트 4개 — 구현이 코어 밖에 있다

| 이름 | 자바 이름 후보 | 부르는 쪽 | 뒤에 무엇 |
|---|---|---|---|
| 사전 조회 | `DictionaryPort` | 후보 검색기 | 메모리 상주 사전 넷 |
| 참조 조회 | `ReferencePort` | 실재 확인 | 엔진 DB · `ref` |
| 설정 조회 | `ConfigPort` | 층 판정기 · 응답 판정기 | `svc.config` |
| 옛주소 조회 | `LegacyAddressPort` | 정제 오케스트레이터 | 어댑터 — 그 뒤에 카카오 |

### 4-4. 반환을 만드는 자리

| 이름 | 자바 이름 후보 | 구현 |
|---|---|---|
| 응답 조립 | `ResponseStrategy` | 교정 전략 · 검출 전략 |

교정은 확정 주소 또는 고를 후보 목록을 내고, 검출은 처리 결과 전체와 실패 목록을 낸다. **두 반환 value를 같은 모양으로 맞추지 않는다.**

## 5. 정제 컨텍스트

요청 하나만큼 살고 끝나면 버려진다. 요청 사이에 살아남는 순간 그것이 곧 상태가 되고 무상태 결정이 깨진다.

| 칸 | 적는 단계 | 읽는 단계 |
|---|---|---|
| 원문 · 우편번호 · 전략 value · 설정식별자 | 진입점 | 전 단계 |
| 조각 목록 | ① | ②③④⑤ |
| 고쳐 읽은 자리 | ① | ⑧ |
| 주소 여부 | ② | 오케스트레이터 |
| 성립하는 표기 집합 | ③ | 오케스트레이터 |
| 갈래별 후보 집합 | ④ | ⑥ |
| 층 결과 | ①④ | ⑧ |
| 건물 후보 집합 | ⑥⑦ | ⑦⑧ |
| 버린 조각 목록 | ⑥ | ⑧ |
| 상세 확정 수준 | ⑦ | ⑧ |
| 등급 · 사유 | ⑤⑧ | 응답 조립 |

**조각 하나가 드는 것** — 원문 위치 · 값 · 걸린 층 · 사전에서 찾았는지 · 정확히 맞았는지 닮은 것만 있었는지.

## 6. 코드의 의도를 검사하는 구조 검사 규칙 8가지

구현 코드를 한 줄씩 읽는 대신 아래를 본다.

| 볼 것 | 어긋난 모습 | 깨진 규칙 |
|---|---|---|
| 갈래를 목록으로 주입받는가 | 하나를 골라 부른다 | 갈래에 우선순위를 두지 않는다 |
| 단계가 다른 단계를 부르는가 | 파서가 관문을 부른다 | 순서를 아는 자리는 하나다 |
| 실재 확인을 지나치는 경로가 있는가 | 닮은 정도로 바로 답한다 | ③단계를 건너뛰지 않는다 |
| 버린 조각이 컨텍스트에 적히는가 | 지역 변수로 사라진다 | 버린 조각을 감추지 않는다 |
| 등급과 사유가 두 칸인가 | 한 칸에 뭉쳐 있다 | 등급과 사유를 합치지 않는다 |
| 코어가 카카오를 아는가 | 코어에서 직접 부른다 | 어댑터로 감싼다 |
| 허용 오타가 어디서 오는가 | 코드에 박혀 있다 | 설정 value로 두고 실행마다 기록한다 |
| 컨텍스트가 요청보다 오래 사는가 | 필드나 캐시로 들고 있다 | 무상태 |
