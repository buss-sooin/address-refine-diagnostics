## 2. 조합별 오류 대응표

### 2-1. 축1: 기본주소 입력 방식에서 생기는 오류

#### `P` 팝업 강제

팝업으로 입력을 강제해도 오류는 없어지지 않습니다. 오류가 생기는 지점이 옮겨 갈 뿐이고, 팝업 때문에 생기는 오류도 따로 있습니다.

| 코드 | 원인 | 결과 | 수준 |
|---|---|---|---|
| P1 | 반환 value `address`에는 검색어 종류에 따라 도로명주소가 들어가기도 하고 지번주소가 들어가기도 합니다. 어느 쪽인지는 별도 값을 봐야 알 수 있습니다 | 같은 칼럼에 도로명주소와 지번주소가 섞여 저장됨 | `[확인]` |
| P2 | 지번과 도로명이 일대다 관계일 때 사용자가 '선택 안함'을 누르거나 대표 주소만 고르면, 여러 후보 가운데 첫 번째 후보가 자동으로 채워집니다. 이 설정은 기본으로 켜져 있고, 공식 가이드도 이렇게 채운 주소가 정확한 주소가 아니라고 밝힙니다 | **형식이 완전하고 실제로 있는 주소이지만 입력한 사람의 주소가 아닌 값** | `[확인]` |
| P3 | 일대다 관계에서는 후보마다 우편번호가 다를 수 있어서, 어느 후보를 고르는지에 따라 우편번호가 달라집니다 | 주소와 우편번호가 서로 맞지 않는 기록 | `[확인]` |
| P4 | 공식 예제는 건물명과 법정동을 괄호로 묶은 '참고항목'을 별도 값으로 반환합니다. 이 값을 기본주소에 붙일지, 상세주소에 넣을지, 버릴지는 컴포넌트를 쓰는 쪽이 정합니다 | 기본주소 끝에 괄호로 묶은 참고항목이 붙은 문자열 | `[확인]` |
| P5 | 시·도 이름을 줄여 쓰는 설정이 기본으로 켜져 있습니다. 단, 세종·제주·강원·전북·전남광주는 줄이지 않습니다 | 같은 팝업에서 받은 값인데도 지역에 따라 줄임말과 전체 이름이 섞임 | `[확인]` |
| P6 | 영문 보기에서 주소를 고르면 영문 주소가 그대로 반환됩니다 | 한글 주소 칼럼에 영문 주소가 저장됨 | `[확인]` |
| P7 | 행정동으로 검색했는데 그 행정동이 법정동과 다르면, 행정동 정보를 함께 표시하고 반환합니다 | 법정동 기준 조회로는 찾을 수 없는 표기가 섞임 | `[확인]` |
| P8 | 도로명으로 검색하면 같은 도로명에 속한 다른 지번이 결과 화면에 보이지 않을 수 있습니다 | 실제와 다른 지번이 선택되어 저장됨 | `[확인]` |
| P9 | 팝업에서 자기 주소를 찾지 못해도 주문은 제출해야 합니다. 기본주소가 비어 있으면 다음 단계로 넘어갈 수 없으므로, 비슷한 주소를 고른 뒤 상세 칸에 실제 주소를 적어 우회할 수 있습니다 | 기본주소는 정상인데 상세 칸에 또 다른 주소가 들어 있음 | `[유도]` |

#### `S` 자동완성 검색

| 코드 | 원인 | 결과 | 수준 |
|---|---|---|---|
| S1 | 검색어를 입력할 때 보여 주는 제안 개수에 상한이 있습니다(기본 10개) | 후보가 상한을 넘으면 정답이 목록에 나오지 않아, 사용자가 비슷한 주소를 고르거나 자유 입력으로 넘어감 | `[확인]` |
| S2 | 사용자가 입력한 검색어 원문이 별도로 반환됩니다 | 아무것도 고르지 않고 화면을 벗어나면 검색어가 그대로 주소로 저장될 수 있음 | `[유도]` |

#### `F` 자유 입력

| 코드 | 원인 | 결과 | 수준 |
|---|---|---|---|
| F1 | 채널마다 주소를 한 칸에 담기도 하고 나눠 담기도 합니다 | 기본주소 뒤에 상세주소가 그대로 이어 붙은 한 칸 | `[확인]` |
| F2 | 스프레드시트 셀 서식 | 우편번호 앞자리 0이 사라짐, 셀 안 줄바꿈, 앞뒤 공백, 셀 병합 잔재 | `[확인]` |
| F3 | 채널마다 열 구성이 다르고, 사람이 복사해 붙여 넣어 취합합니다 | 열이 밀림, 배송 메시지나 연락처가 주소 칸에 섞임 | `[확인]` |
| F4 | 어떤 표기도 막지 않습니다 | 시·도 생략, 도로명과 건물번호를 붙여 씀, 도로명과 지번을 섞어 씀, 건물명만 적음 | `[유도]` |

### 2-2. 축2: 상세주소 입력 방식에서 생기는 오류

| 코드 | 값 | 원인 | 결과 | 수준 |
|---|---|---|---|---|
| T1 | 자유 텍스트 | 표기 형식을 강제하지 않습니다 | 동·호 표기 변형이 모두 이 칸에 모임 | `[유도]` |
| T2 | 자유 텍스트 | 기본주소를 팝업으로 고정하면 사람이 자유롭게 쓸 수 있는 칸이 이 칸 하나만 남습니다 | 오류가 이 칸에 몰림 | `[유도]` |
| T3 | 자유 텍스트 | 반환 value에 공동주택 여부가 있지만, 상세주소 입력을 강제하지 않게 구현할 수도 있습니다 | 아파트인데 동·호가 없음. 형식 오류는 아니지만 배송할 수 없음 | `[확인]`+`[유도]` |
| D1 | 동·호 분리 | 칸 이름이 '동'인데 사용자가 "208동"처럼 단위까지 입력합니다 | 두 칸을 합칠 때 단위가 겹침 | `[유도]` |
| D2 | 동·호 분리 | 단독주택이나 오피스텔에는 동이 없는데 동 칸이 필수 입력입니다 | 빈칸을 채우려고 넣은 값(`1`, `-`, `없음`)이 들어옴 | `[유도]` |
| D3 | 동·호 분리 | 두 칸을 한 문자열로 합칠 때 쓰는 구분자가 시스템마다 다릅니다 | 받는 쪽에서 다시 나누지 못함 | `[유도]` |
| M1 | 지도 핀 | 좌표를 주소로 바꿀 때 건물 경계를 기준으로 삼습니다 | 옆 건물 주소로 확정됨 | `[유도]` |
| M2 | 지도 핀 | 핀은 건물까지만 가리킵니다 | 동·호는 여전히 사람이 입력하므로 동·호 표기 변형(T1)이 그대로 남음 | `[유도]` |

### 2-3. 축3: 검증 시점에 따라 생기는 오류

| 값 | 원인 | 결과 | 수준 |
|---|---|---|---|
| `I` 입력 즉시 | 팝업과 자동완성이 사실상 입력 즉시 검증하는 역할을 합니다 | 기본주소 오류는 줄지만, 오류가 상세주소 칸으로 옮겨 감 | `[유도]` |

### 2-4. 실제로 쓰이는 조합

축마다 값이 3개이므로 조합은 27가지이지만, 전부 실제로 쓰이지는 않습니다. 실제로 쓰이는 조합은 아래와 같습니다.

| 조합 | 주로 쓰이는 곳 | 주로 생기는 오류 | 수준 |
|---|---|---|---|
| `P-T-I` | 일반 주문 화면 | P1~P8과 T1·T2. 오류가 상세 칸에 몰림 | `[유도]` |
| `P-D-I` | 동·호를 나눠 받는 배송 관리 화면 | P1~P8과 D1~D3 | `[유도]` |
| `P-T-N` | 외부 업체 팝업으로 받은 값을 그대로 넘기는 연동 | P2가 아무 검증 없이 통과함 | `[유도]` |
| `S-T-B` | 앱 자체 검색 | S1·S2와 재시도 변형 | `[유도]` |
| `F-T-N` | 엑셀 배치, 외부 연동 수신, 전화·수기 접수 | F1~F4 전부와 오류 발견 지연 | 본인 실무 |
| `F-T-B` | 자유 입력을 받고 서버가 반려하는 화면 | F1~F4와, 이유 없는 반려 때문에 늘어나는 표기 변형 | `[유도]` |
| `*-M-*` | 위치 기반 주소 설정 | M1·M2 | `[유도]` |

## 3. 응답 종류와 사유 종류 (확정)

### 3-1. 응답은 5가지입니다

| 응답 | 어떤 상태인가 | 사용자에게 보여 주는 말 |
|---|---|---|
| 확실한 성공 | 후보가 하나이고 버린 조각이 없음 | (보여 주는 말 없음) |
| 확인 권장 | 후보가 하나이지만 그대로 받으면 안 되는 이유가 있음 | "이 중 맞는 것을 골라주세요" |
| 후보 여럿 | 후보를 하나로 좁히지 못해 2개 이상 남음 | "이 중에 있나요?" |
| 실패 | 후보를 하나도 찾지 못했고 고칠 방향도 없음 | "여기가 잘못됐습니다" |
| 수정 제안 | 후보를 하나도 찾지 못했지만 고칠 방향은 있음 | "혹시 이것 아닌가요?" |

**확인 권장과 후보 여럿은 성격이 완전히 다릅니다.**
확인 권장은 후보를 하나로 좁혔지만 그대로 받으면 안 되는 이유가 따로 있는 상태입니다.
후보 여럿은 후보를 하나로 좁히지 못해 고를 후보가 2개 이상 남은 상태입니다.

### 3-2. 등급과 사유를 따로 정합니다

```
등급  =  남은 후보 수로 정함          1이면 확실 · 2 이상이면 후보여럿 · 0이면 실패
사유  =  버린 조각이 있으면 붙임      등급과 무관함
등급이 확실이고 사유가 있으면 확인 권장으로 응답함
```

등급과 사유를 한 칼럼에 합치지 않는 이유는 조건이 늘어날 때를 대비하기 위해서입니다. 두 값을 합치면 조건의 조합마다 등급을 새로 만들어야 하지만, 나눠 두면 사유 value 하나만 더하면 됩니다.

**후보 수는 건물관리번호 단위로 셉니다.** 건물관리번호는 25자리이고 건물마다 하나씩 붙으며 중복되지 않습니다. 후보 수를 세는 일에는 사람도 LLM도 관여하지 않습니다.

이 규칙은 특정 회사 팝업의 동작을 피해 가려고 만든 임시방편이 아닙니다. 지번만 입력한 주소는 원래 후보가 하나로 좁혀지지 않으며, 엑셀로 올리든 전화로 받아 적든 마찬가지입니다. 따라서 이 규칙은 주소 체계 자체에서 나오는 일반 규칙입니다.

### 3-3. 확인 권장으로 응답하는 경우는 3가지입니다

확인 권장은 후보를 하나로 좁혔지만 그대로 받으면 안 되는 이유가 있을 때 응답합니다. 어떤 이유인지는 사유 종류로 구분합니다.

| 무슨 일이 있었나 | 사유 종류 | 근거 |
|---|---|---|
| 지번과 도로명이 일대다 관계여서 첫 후보가 자동으로 채워졌습니다 | 정보 부족 | P2 `[확인]` |
| 입력한 토큰 일부를 버리고 나머지 토큰으로 후보를 좁혔습니다 | 입력 오류 | `03-pipeline.md` 4절 |
| 옛 표기를 현재 표기로 바꿨습니다 | 입력 오류 | `03-pipeline.md` 8절 |

근거가 있는 것과 없는 것을 구분해 둡니다.
- 근거가 있는 것: 공식 가이드에 자동 채움 동작이 적혀 있습니다. `[확인]`
- 근거가 없는 것: 자동 채움이 실제 배송 오류로 이어졌다는 실무 관측은 없습니다.
- 따라서 확인 권장은 **실제로 겪은 오류에 대응해 만든 장치가 아니라, 구조상 생길 수 있는 오류를 미리 막는 장치입니다.**

### 3-4. 확인 권장을 남발하면 경고가 의미를 잃습니다

경고가 늘 뜨면 경고가 없는 것과 같습니다. 그래서 확인 권장은 등급을 만들었다는 사실로 평가하지 않고, **하나로 좁혀지는 주소에 쓸데없는 경고가 얼마나 드물게 붙는지**로 평가합니다. 확실한 성공이 나와야 하는 케이스에 경고가 뜨면 오탐입니다. 오탐은 기대 정제 값으로 측정할 수 있습니다.

### 3-5. 사유 종류는 3가지입니다

| 사유 종류 | 뜻 | 누가 고치는가 | 채점 방법 |
|---|---|---|---|
| 입력 오류 | 잘못 쓰셨습니다 | 사용자 | 사유대로 고쳐 다시 넣으면 성공하는가 |
| 정보 부족 | 정보가 모자랍니다 | 사용자 | 제시한 후보 안에 정답이 있고, 정답을 고르면 확실한 성공이 되는가 |
| 참조 데이터 없음 | 우리 쪽 데이터에 없습니다 | 우리 | 참조 데이터를 보정하면 성공하는가 |

**기대 정제 값 한 줄은 칼럼 5개로 이루어집니다.**
`입력 value / 기대 사유 / 사유 종류 / 교정 후 기대 정제 값 / 근거`

## 4. 케이스 목록

### 4-0. 네 묶음은 케이스를 뽑은 출처가 서로 다릅니다

| 묶음 | 뽑은 출처 | 무엇을 시험하나 |
|---|---|---|
| A군 | 팀프레시 실무 | 실무에서 실제로 겪은 문제를 지금 시스템이 해결하는가 |
| B군 | 주소 입력 화면의 구조 | 입력 화면이 만들어 내는 값을 받아 처리할 수 있는가 |
| C군 | 글자 변형 생성기 | 표기가 달라져도 같은 결과가 나오는가 |
| D군 | 우리 알고리즘에서 처리 흐름이 나뉘는 지점 | 처리 흐름의 분기마다 한 번 이상 실행되는가 |

A군, B군, C군은 모두 입력이 어떤 식으로 잘못 들어오는지를 기준으로 뽑았습니다. D군만 반대 방향에서 뽑습니다. 처리 흐름이 나뉘는 지점을 먼저 세고, 각 분기를 지나가는 입력을 만듭니다. `서울특별시 만안구`처럼 **글자는 하나도 틀리지 않았는데 처리에 걸리는 입력**은 A군, B군, C군에서는 나오지 않습니다.

네 묶음의 결과를 합쳐 하나의 통과율로 내지 않습니다. 묶음마다 측정하는 대상이 다르기 때문입니다.

표의 등급은 검출 전략 기준입니다. 채운 값을 알리는 사유코드 4개(`SGG_INFERRED` · `UNIT_TOKEN_RESTORED` · `LEGACY_NAME_MAPPED` · `TYPO_CORRECTED`)가 붙은 줄은 교정 전략에서 확실한 성공이 됩니다. 규칙은 `03-pipeline.md` 4절 「채운 값도 코드로 알립니다」에 있습니다. 두 전략의 결과가 이와 다르게 갈리는 줄은 표에 전략마다 따로 적었습니다.

서울에서는 A4에 해당하는 사례를 찾지 못했습니다. 2024년 8월분과 2026년 7월분을 비교해도 서울의 시도·시군구·읍면동·도로명 이름이 바뀐 것은 0건입니다. 그래서 A4 케이스는 다른 시도에서 뽑았습니다. 이 유형은 지역과 상관이 없고, 인천 서구는 지금도 흔히 쓰는 표기입니다.

갱신 시점 차이로 매칭에 실패한 입력(A5)을 두 줄로 나눈 이유는 대응 사전의 항목이 시간이 지날수록 늘어나기 때문입니다. 같은 입력이라도 대응 사전에 항목이 있을 때와 없을 때 응답이 달라집니다. 두 경우 모두 주소를 찾고 등급도 똑같이 확인 권장입니다. 달라지는 것은 사유 코드로, 대응 사전에 있으면 옛 이름을 바꿨다는 코드가, 없으면 입력 일부를 쓰지 않았다는 코드가 붙습니다.

A5 유형이 다른 유형과 성격이 다르다는 점은 그대로입니다. 입력은 입력하던 때에는 옳았고, 우리 참조 데이터에 그 이름이 없을 뿐입니다. 다만 사용자가 현재 이름으로 다시 쓰면 해결되므로 사용자가 고칠 수 있는 문제입니다. 그래서 A5의 사유 종류를 「참조 데이터 없음」이 아니라 「입력 오류」로 적습니다.

A5에 해당하는 가장 큰 사례는 2026년 7월 1일 전남광주통합특별시 출범입니다. `[확인]`
전라남도와 광주광역시가 폐지되고, 전남 22개 시군과 광주 5개 구가 하나로 통합되었습니다. 2026년 7월 전체분에는 이 변경이 이미 반영되어 있어서 옛 두 이름이 자료에 없습니다. 그래서 이 사례의 대응 관계는 과거연동으로만 채울 수 있습니다.

과거연동에 쓸 세트는 2024년 8월 전체분입니다. [전량] 2026년 6월 30일 기준 자료에도 이미 전남광주통합특별시가 들어 있어서, 한 달 전 세트로는 옛 이름을 얻을 수 없습니다. 행정안전부가 변경을 시행하기 전에 자료에 미리 반영하기 때문입니다. 자세한 내용은 `04-source-data.md` 11-4·11-5절에 있습니다.

### 4-5. 분류 불가: 일어난 것은 확인했지만 유형을 모르는 사례

실무에서 배송이 잘못된 사례가 있었습니다. 정제는 성공으로 끝났지만 결과가 틀린 경우입니다.
하지만 이 사례가 어느 유형에서 생겼는지는 알 수 없습니다. 당시 시스템이 실패 사유를 남기지 않아서 나중에 분류할 수 없습니다.

- 이 사례는 A군에 넣지 않습니다. 유형을 모르는 사례는 A군 케이스가 될 수 없기 때문입니다.
- 이 사례는 커버율 계산의 분자에도 분모에도 넣지 않습니다.
- **이 항목은 지우지 않고 남겨 둡니다.** 케이스가 없다는 사실을 감추지 않고, 왜 없는지 확인할 수 있게 하기 위해서입니다.
- 이 사실 자체가 이 솔루션이 해결하려는 문제를 보여 줍니다. 사유를 남기지 않으면 나중에 아무것도 알 수 없습니다.
